# Security and Trust Boundaries

## Threat model

CE Decky consumes untrusted third-party artifacts and starts a Windows program inside a running game's compatibility prefix. A `.CT` may contain Auto Assembler and Lua capable of arbitrary actions with the user's privileges. That content is readable in the panel before it is authorized, which is a read and never a run: every section goes through the same verified-blob read and the same refusals inspection uses, is bounded on size, line count and line length, and is normalized against invisible and bidirectional characters so a script cannot render as something other than what it is. What that normalization or a bound removed is stated on screen, because the file is what would run and not the rendering of it. An embedded file's bytes are never returned to the panel; only its declared name and size are. Provider pages/redirects are untrusted network input. Steam state is read-only to CE Decky: it observes app identity and never writes launch options or any other Steam configuration.

## Non-negotiable controls

- Importing a table never means executing it.
- Bind any future executable-content acknowledgement to exact table SHA-256.
- Never label a provider or author as inherently safe.
- Do not log cookies, auth headers, signed query strings or direct artifact URLs, lock tokens, passwords, response bodies or table code. Structured log fields are name-aware, control/bidi-cleaned and length-bounded; unexpected diagnostics include frame identities without locals. HTTP dependency request logging stays at warning or above so it cannot copy a signed URL into the ordinary plugin log.
- A provider's identity is declared once, in the provider registry: display name, rank, adapter kind and host allowlist live on one definition, and the downloader's host policy is derived from it rather than repeated. The registry is read-only, so a caller cannot change a provider's identity while allowances already derived from it stay behind. Host policy stays backend-only and is never serialized to the frontend, which sees an opaque artifact ID.
- Refusing a source because it defends itself against automation is a factual claim, and it carries the same evidence burden as using one. Name the exact control observed, on the exact route, with what the response was: a challenge interstitial, an authentication redirect, a captcha actually demanded by the download path. An unexplained redirect, a script-driven control, or the mere presence of fingerprinting code somewhere on the page is not that, because analytics collects fingerprints too and a legacy URL redirects everyone. Before recording such a refusal, rule out the ordinary explanations by test and write down which were ruled out: cookies, `Referer`, `Accept` headers, request parameters, and whether an honest client and a browser are actually treated differently. A refusal recorded on a guess is worse than no verdict, because it is durable, it stops anyone looking again, and it wrongly accuses the operator of something they did not do.
- `robots.txt` is honoured as what it is, a crawling directive, and the two halves of a provider are treated differently. Discovery crawls only what a site permits: its declared sitemap and its allowed listings, never a disallowed search, feed, pagination or attachment-enumeration route. Retrieving one artifact the user explicitly chose is not crawling and is not governed by that directive, because it is the user's own retrieval performed through the plugin rather than an index being built. This distinction never relaxes anything else: the artifact still passes host policy, HTTPS, redirect revalidation, public-address checks, digest verification and executable-content consent, and a source that requires an account, defeats a bot challenge, or forbids the retrieval itself rather than its crawling remains refused.
- Direct downloader uses provider host allowlists, rejects loopback/link-local/private/multicast/other non-public literals, resolves and rejects any hostname for which **any** A/AAAA answer is non-public, and repeats the checks on every redirect. The system resolver is the explicitly accepted resolver-to-connect trust boundary: `httpx` may resolve again while connecting, but the platform resolver is trusted not to return a different attacker-controlled address between policy validation and the verified TLS connection. This does not weaken certificate or hostname verification.
- HTTPS-to-HTTP downgrade is rejected for provider downloads.
- CE Decky offers two destructive actions, and neither is ever implicit. Removing one stored table is the first, described below; deleting plugin data is the second and is the one that can take the whole table tree with it.
- Deleting plugin data names one of three fixed scopes, never a path; the paths come from the plugin's own owned roots; a symlink is unlinked rather than followed, so recursive deletion cannot leave the managed tree; and directory contents go while the directories are re-established with their symlink and resolution guards re-applied. It is refused outright while anything is still executing out of that tree: a Cheat Engine process CE Decky owns, a managed installation still unpacking into it, or a table download that still owns a staged file. The middle scope deliberately keeps the Decky settings directory, because which Cheat Engine is registered lives there and deleting it while keeping the installation orphaned a multi-gigabyte tree the panel then reported as absent. Unreadable profile or session state does **not** refuse it, because a full reset is the controller-reachable way out of that state. `_uninstall()` remains non-destructive; this is a separate, explicitly confirmed user action.
- Removing one stored table destroys exactly the bytes of one exact SHA, chosen from the plugin's own catalogue. The frontend names a digest and never a path, and the path is walked from the store's own root with every component required to be a real directory this store owns: a link anywhere along it, not only at the file itself, is refused rather than followed, because a digest directory that is a link holds an ordinary file belonging to somebody else. A link at the file itself is unlinked as the entry it is. It takes two deliberate presses, it is refused while any game has that table selected, it is serialized with every other profile and table mutation, and it removes the bytes before the record so that a failure leaves a table that lists as missing its file rather than storage nothing can name. A directory where the file belongs is refused outright.
- Archives use list/preflight before extraction, normalized-path traversal/symlink/duplicate checks, member/aggregate/selected-output limits, staging, then exact `.CT` validation. ZIP extracts only the selected member in-process. The 7-Zip adapter, which reads `.7z` and `.rar` through one contract, streams only the selected member and kills the child if declared/actual bounds are exceeded; an encrypted member of either is disabled because command-line passwords would leak through the process list.
- Reading what a game starts, and what its folder holds, is read only, bounded and refuses anything it cannot prove. `game_files.py` resolves one install directory from the AppID's own `appmanifest` under the existing Steam-library discovery, and refuses a manifest that declares a different AppID, an `installdir` that is anything but one path component, and a resolved directory outside the library that named it. `steam_launch.py` reads Steam's own `appcache/appinfo.vdf` under the same discipline: the file is opened without following its final component and only if it is a regular file, its size, key table, per-app record length, map nesting and reported entries are each bounded, a container version or value type it does not know is refused rather than skipped, and a record whose declared length would run past the file ends the read. A launch path is taken only where it is relative, free of `..`, and ends in a basename this plugin would accept as a target process; it is then resolved under the game's own install directory and reported only if the file is actually there and inside it. The folder walk is bounded by depth, by entries examined and by results, follows no symlink, and reads no file content. The same AppID installed under two libraries is a stated refusal, not a choice between them. What either produces is candidates on a picker the user confirms, never an authorization: not even Steam's own record says which executable owns a game's memory, because a game that starts through a launcher of its own declares the launcher, and the panel says so where the choice is made and again the first time the game runs without it.
- CE Decky never writes Steam state. The frontend reads AppDetails for identity only; no code path calls `SetAppLaunchOptions`, `SetShortcutLaunchOptions`, or writes `shortcuts.vdf` or `localconfig.vdf`, and `scripts/verify_repo.py` fails the build if those setters reappear anywhere under `src/`. `shortcuts_vdf.py` does carry a binary serializer, and it is a validator rather than a writer: a parse is accepted only when re-serializing the parsed nodes reproduces the original bytes exactly, so a file this backend cannot reproduce is refused instead of half-understood. Nothing calls it to produce a file. Cheat Engine is started as a plugin-owned POSIX process group instead, so no failure can leave Steam configuration owned by CE Decky.
- Opening an external page never depends on a private Steam surface. It goes through Decky's own `Navigation`, falling back to an ordinary `window.open`, and the URL is bounded, HTTPS, and rejected outright if it carries embedded credentials. A private surface may never be required for anything the workflow needs.
- Standard Decky `_uninstall()` is non-destructive because Decky invokes uninstall semantics during update/reinstall.
- Managed data is removed in bulk only through the explicit `Prepare for removal` workflow, and only once no plugin-owned Cheat Engine process or prepared session is still live. Removing one table is the other route and is bounded by the exact-SHA rules above; nothing else deletes persistent managed data, and neither route is ever implicit.

## Runtime session / bridge boundary

One runtime RPC carries at most `MAX_RUNTIME_RPC_COMMANDS` (64) commands and only one batch may be unacknowledged at a time, so a frontend defect cannot queue unbounded work against a running game. The resident bridge never evaluates mutable session files as Lua. Descriptor, control and status use a strict percent-encoded line protocol with bounded size/count. Session identity binds AppID, exact table SHA, exact CE executable SHA, authoritative descriptor SHA-256 and UUID. The bridge also checks `CE_DECKY_DESCRIPTOR_MD5` with CE's documented `md5file` immediately before and after reading the bounded descriptor. Bridge patterns are held to Lua pattern syntax by `tests/test_bridge_asset.py`, because a regex-only construct is not an error in Lua: it is accepted as literal text, so a guard written that way matches nothing and fails open where it was meant to refuse. MD5 is **not** the trust anchor and does not replace SHA-256; it is an early CE-side tamper/race guard because the public CE Lua API does not document a SHA-256 file helper. Runtime generation `0` is reserved for startup; backend sequencing derives the next generation from current control/status and preserves unacknowledged commands across frontend reloads. A bounded host heartbeat TTL marks old status files disconnected.

Runtime RPCs are also revalidated on the host against a fresh exact-SHA static table inspection. A caller cannot address an arbitrary MemoryRecord ID merely by bypassing the QAM: IDs must exist uniquely in the exact selected table, group-header records are presentation-only and rejected as mutation targets, `set_value` is allowed only for value/dropdown controls, and read-only dropdowns accept only declared values - a record that declares itself read-only while declaring no values therefore accepts none, in the inspector's classification, the picker, the live command path, the legacy startup write and the session plan alike. Record query/Active/Value commands additionally require a fresh current bridge that reports a positive attached PID; the CE-side bridge repeats the attachment check immediately before execution to close the detach-after-host-preflight race. Process listing and explicit retry-attach remain available while the fresh bridge is unattached.

The compact cheat picker does not make UI state authoritative. Apply first queries the current exact session, sends only a bounded diff through the existing generation/ACK protocol, and re-queries before remembered state is persisted. `set_remembered_cheats` and `set_configured_values` re-inspect the verified exact table on the host and reject missing/ambiguous/group IDs and invalid read-only dropdown values; a configured value must additionally target a value/dropdown record and may not be blank or Cheat Engine's unreadable placeholder. Autoload is profile- and exact-SHA-bound: it requires the selected SHA's existing execution consent and target process; selecting a new SHA never inherits remembered IDs or consent.

Foreground recovery never chooses a process by title or launches a focus helper outside the bridge. It requires the attached PID, a top-level window with that exact owner, visibility and non-minimized state; ambiguous candidates are skipped. Ownership is checked again immediately before the bounded Win32 request. It neither synthesizes input nor attaches thread input queues. A posted application notification and an observed foreground change are recorded separately.

Artifact resolutions and positive compatibility evidence are advisory, bounded, strictly parsed stores. Neither can authorize execution, suppress digest verification or block use of a local table. Successful compatibility requires backend-held proof of an acknowledged activation and a subsequent active readback in the same fresh current session, finalized only after the frontend operation succeeds or the exact backend-prepared startup completes with successful leaf readback. A client boolean is never proof. Game versions and Steam AppState build IDs are optional observations; unknown values do not become guessed fingerprints. Support bundles include these records and the optional focus telemetry within their existing budgets, without collecting game binaries or manifest contents.

## Anti-cheat boundary

The project is for offline/single-player use. It does not automate disabling or bypassing VAC, EAC, BattlEye or other anti-cheat systems, and it does not attempt to hide CE or the plugin from anti-cheat software. If a selected game is known to depend on anti-cheat, the safe product behavior is warning/refusal rather than bypass automation.

That refusal is enforced from one signal on both sides of the RPC boundary: an exact known anti-cheat executable basename in the running game's observed process set. Table review, manual start and Auto-load refuse it in the panel, and the attached-launch supervisor refuses it again immediately before it spawns anything, because a stale overlapping frontend or a direct RPC reaches the supervisor without the panel's guard. Identification is by exact basename only - never a game title, a directory name, or any other inference - and no code path disables, hides from, or otherwise interferes with the anti-cheat itself.

## Cheat Engine distribution boundary

No Cheat Engine source or binary is included in Git or release artifacts. The official FAQ currently states that the source is provided for education/transparency and does not grant a license to publish derivative CE versions. Managed CE setup is therefore an explicit user-initiated, official-origin operation: a packaged read-only release manifest pins the exact HTTPS host, byte size, SHA-256 and the SHA-256 of the reviewed publisher's `SubjectPublicKeyInfo`. Neither the installer nor the download helper is ever executed. When the pinned URL stops serving the reviewed bytes, the current installer URL is rediscovered from the pinned download page and the download helper it links to; each hop's host allowlist is derived from what the previous, pinned hop actually named, so a redirect cannot widen it, and only a failure of the download route itself - never a local I/O failure - starts that path. A rediscovered artifact is accepted only on the reviewed SHA-256; the pinned publisher key never authorizes an install, and native extraction is pinned to the reviewed artifact's format regardless. The signature is still checked - the Authenticode digest is computed in-process and the PKCS#7 signature verified by `openssl smime`, with no certificate chain or revocation standing in for the pin - so that a different release from that publisher is reported as a packaging limit rather than as an untrustworthy download; a missing `openssl` only costs that distinction. The signature establishes the publisher, never a version ordering. The manifest may set its rediscovery policy to `null` to ship without the route at all. The backend downloads into plugin-owned staging, verifies the complete PE artifact, then natively parses only the reviewed CE 7.7 format: loader/metadata CRCs, layout and CE XOR decoding, deterministic file/location tables, bounded `{app}` paths, per-payload SHA-256 and final PE signatures must all validate before a bounded regular tree can be atomically promoted. Diagnostic hash overrides exist only in the standalone extraction tool and have no production RPC. `Import existing Cheat Engine` remains a controller-accessible fallback.

A forced managed reinstall always downloads a fresh reviewed artifact and verifies it before atomically replacing the plugin-owned artifact cache; an interrupted refresh retains the prior cache. It never destroys the last validated managed installation before replacement validation: promotion moves the old tree to an owned same-filesystem backup, validates the promoted tree, and restores the backup on any promotion/post-validation failure. The service reserves the CE identity/materialization mutation boundary before asynchronous managed setup begins and retains it through final registration; this prevents concurrent session/runtime/launch/import work from observing a tree while it is being replaced. A completed installer operation is cleared only after the registered CE identity has been durably persisted, so a failed final commit remains safely resumable. One exact-ID in-memory completion receipt makes an overlapping observer's completion retry read-only without repeating the config mutation; polling that consumed operation still reports it as unknown; the receipt is discarded before the next managed setup and never authorizes another operation ID.

Some Steam builds expose no running-app query to the frontend at all, which would force every user to select the game by hand. When that query is absent, the backend offers running-game *candidates* from the same bounded process-table scan: only `SteamAppId`, Steam's own declaration in the process environment, is accepted; a 64-bit `SteamGameId` is not an AppID and is ignored; candidates are matched against the Steam library before any of them can be selected; and an incomplete or oversized scan is reported as unavailable rather than as a short list, so a truncated observation can never look like "that game is not running". This proposes a selection only. It is never the source of a compatibility prefix, Proton identity, or launch path, all of which remain independently resolved from Steam library metadata and required to agree.

The managed or user-selected CE installation is treated as read-only source input. Current CE startup code derives its autorun directory from the executable directory, so bridge-enabled operation uses a **private local runtime copy** under CE Decky's managed root instead of altering that installation. That copy is private machine state, never a distributable artifact. Its physical aggregate key keeps Proton/Wine launch paths bounded while the manifest retains exact executable/tree/bridge identities. Because CE's Win32 autorun enumeration is unordered, a generated private-copy `main.lua` loads the exact bridge first and then the byte-preserved source `main.lua`; the source installation is never changed. Materialization is fail-closed on executable SHA drift, source-tree identity drift during copy, symlinks/non-regular files, excessive tree size/count, copied-executable/tree mismatch, reserved bootstrap/bridge collision, or damaged immutable runtime state. Recovered runtime commands additionally require the strict manifest schema, exact aggregate directory key, manifest root/executable paths, prepared CE SHA, packaged bridge SHA, and the current executable/bridge bytes to agree; inability to read the packaged bridge fails closed. The exact Proton tool identity remains in the durable launch record and was independently verified immediately before execution; it is launch/ownership identity, while resident command-protocol compatibility is the CE/tree/bridge runtime tuple.

## Table-store execution boundary

Catalogue metadata is durable before blob publication. A metadata failure never triggers deletion of shared content. Startup reconciliation accepts only real owned digest paths and bounded CT bytes whose SHA matches the directory identity; it preserves every existing metadata record, records recovery/refusal in the support log, and grants no consent. Deletion syncs blob absence before removing metadata, then syncs the metadata directory. Rename/unlink failures after authority moved report durability uncertainty, including repair paths; bulk removal cannot report success before its retained directory is synced.

The table list uses cheap presence/size checks for UI responsiveness. **Presence is not execution integrity.** Any future path that passes a stored table to Cheat Engine must resolve it through `TableStore.verified_blob(sha256)` immediately before session preparation; that method recomputes SHA-256 and fails closed even on same-size tampering.

## Plugin self-update boundary

CE Decky can install its own newer release. Two things make that different from everything else here: it fetches an artifact this project publishes rather than a third party's, and it asks a privileged local service to install it.

- The release route is `https://api.github.com/repos/goooroooX/CE-Decky/releases/latest` and the archive and checksum assets that release names, restricted to GitHub's own release-asset hosts. It goes through the same downloader as everything else, so HTTPS is required, loopback/link-local/private/multicast literals and any hostname with a non-public answer are refused, and the checks are repeated on every redirect. Its host policy is declared in one place and deliberately separate from the GitHub table source's: switching that source off must not disable updates, and switching updates off must not disable that source.
- What may be installed is decided before anything privileged happens. The tag must parse as a version this project publishes and be strictly newer than the running one; a draft or a prerelease is refused; the release must carry both its archive and the `SHA256SUMS` published beside it; the checksum file is fetched first and on its own, so a release that cannot say what its archive is costs no download; and the downloaded archive's SHA-256 must equal the digest that file states for that exact filename. A mismatch installs nothing, keeps nothing and deletes the staged bytes: unverified bytes are never offered for a manual install either.
- The privileged half is Decky's own. The plugins directory belongs to root and nothing in this plugin runs as root; Decky's loader exposes an authenticated JSON RPC on loopback, hands its token to any local process that asks for it, and installs a plugin from a URL the caller names. CE Decky uses exactly two of its routes, `utilities/install_plugin` and `utilities/restart_webhelper`, over loopback HTTP only, with a `file://` URI for an archive it verified itself. Decky's own install confirmation is answered programmatically, and every field of that prompt is checked against what was asked for: another plugin's name, another version, another digest, or a second prompt for one install are each refused. The user's own press on this plugin's confirmation is what authorizes the whole sequence, and that dialog states the version change, the interface restart and that only the download can be stopped.
- The installer is a detached process, because Decky stops this backend while replacing it. It runs a system `python3`, in its own session, with the loader bundle's dynamic-linker variables undone, with a fixed argument list and no shell, and it is given only paths this plugin owns. It writes one result file the next backend consumes. Nothing about it is reachable from the frontend: the panel names no URL, no path and no digest, and asks only for a version it was offered.
- Automatic checking is a network behaviour the user can end. It is off the moment the switch in Advanced is off, it happens only after recent table-search activity and at most once per interval, and it sends one unauthenticated GET carrying nothing about the user or the device beyond what any HTTP request carries.

## Unload / blocking-I/O boundary

Python worker threads created by `asyncio.to_thread()` cannot be stopped by cancelling their awaiter. CE Decky therefore distinguishes cooperative async operations from bounded blocking filesystem mutations. Cooperative provider/network work is cancelled and awaited on unload; local blocking imports/hashes are shielded and **drained before `_unload()` completes** so Decky cannot report the plugin unloaded while a worker continues mutating state.

## Local-state integrity hardening

The implementation treats persisted and imported local files as potentially stale or externally modified. Reads of exact runtime/table/JSON state are bounded and do not follow the final symlink component; critical imports compare stable descriptor identity before/after reading. Managed table subdirectories are revalidated before use, Windows/Wine filename ambiguity is rejected before private-runtime materialization, and strict JSON rejects duplicate keys, non-finite numeric constants and invalid Unicode. Runtime heartbeat bytes and modification time are captured from the same open file descriptor so an atomic path replacement cannot splice content from one heartbeat with timing metadata from another.

## Provider adapter boundary

The host allowlists, the rejection of non-public addresses and the refusal of an HTTPS-to-HTTP downgrade are in **Non-negotiable controls** and hold for every source alike. What follows is what each adapter is additionally held to, one source per entry.

A URL a provider declared while a search runs is held to the transport's structural policy before any row promises a download from it, and an entry in a provider's own sitemap is held to it before contributing identity to that provider's cached index, so a document with the wrong root or an entry from another origin cannot poison an index that is then recorded as complete. A failed download that ends as provider-unavailable is recorded against that provider with its bounded reason and, where the provider stated one, its status, while the deadline it had already named is preserved rather than overwritten.

Anonymous adapters never extract browser cookies, accept account credentials, or perform global GitHub search.

- **FearLess** discovery uses only its readable bounded `viewforum.php?f=4` listing, never the challenged search route; its resumable cache contains bounded topic IDs/titles and page offsets only, numeric topic identities are digit-count bounded on both network and cache input, and only locally ranked matches authorize a bounded topic fetch. Page zero authorizes multi-page offsets only through consistent explicit page-number/offset relations that fit its advertised totals; ambiguity fails that page closed, and the one-page case authorizes offset zero without inventing a stride. A later page may reuse that already-proven stride when it exposes no independent one, but its page identity and totals must fit and explicit contradictory geometry still fails closed.
- **Playground** acquisition uses only the anonymous endpoint and exact parameters called by the site's public client JavaScript. Its bounded countdown lock token and temporary CDN URL remain in memory, never enter frontend responses/cache/provenance/logs, and do not weaken exact host, DNS, redirect, or TLS validation. Artifact CDN authority remains an explicit exact-host allowlist: target evidence currently covers `dl1.gamedl.ru` and `dl3.gamedl.ru`, not a wildcard or guessed sibling.
- **VGTimes** discovery and acquisition are anonymous and hold no account. Its game index is bounded slugs read from the declared sitemap, parsed as whole XML documents rather than by pattern, so a shard that stopped early is refused instead of yielding the prefix it managed; a cached slug that is not a slug drops the whole index rather than being read around, because a slug reaches a URL. The download chain's routes, request fields, countdown and refusal handling are read from the site's own page and client module rather than frozen in the adapter, and a field the module asks for that this client cannot honestly supply fails the chain instead of being invented. The file server is declared by the page, so it is accepted only when it sits under the provider's own domains, and the exact per-acquisition host policy is the site plus those declared servers, never a wildcard. The download token and the solved challenge stay in memory and never enter results, cache, provenance or logs. Nothing the site returns is executed: the challenge script is unpacked by substitution over its own dictionary and read with bounded expressions, its blobs and image are size-bounded, and the AES-CBC used to read them is a decrypt-only pure-Python implementation checked against the NIST SP 800-38A vectors. The object sent back carries only constants the server supplied, values read from the image it supplied and this client's own timing; the automation-probe slot goes out empty, no code path fills it, and the URL builder refuses a non-empty one. The digest the item page advertises is checked against the downloaded bytes, and the published archive password stays backend-owned like every other provider hint.
- **GitHub** discovery is anonymous, bounded and unauthenticated, and it is still not a global code search: CE Decky queries the repository index only, never GitHub's code search, and holds no account or token of any kind. A search spends a bounded number of index queries and inspects a bounded number of ranked repositories, and an exhausted anonymous budget is read as the wait GitHub describes it as, from the reset timestamp it returns with HTTP 403, rather than as a provider failure. The optional repository-index cache is bounded by bytes, query count and age, contains only normalized candidate metadata, and is parsed through the same repository grammar as a network answer before use. It authorizes candidate selection only: release, tree and artifact reads remain live, and every URL component is rebuilt and revalidated. A repository name, branch and committed path all reach a URL, so each is validated against its own grammar before it does: a branch carrying a `..` segment is refused rather than relied on being percent-encoded, and a repository whose search answer names no branch this understands keeps no branch at all rather than acquiring the likeliest one, so the committed-table route is skipped for it instead of built on a guessed ref. A tree answer is used only when it declares itself complete, because completeness is stated on every one of them and an answer that does not say so has not claimed to be whole. Every field that ends up in a URL is read whole or not at all: truncating one before validating it is how a value that was too long becomes a different value that passes, which is the same guessed path arrived at differently. Release assets keep the advertised SHA-256 check they already had; a table committed in a tree is verified against git's own object name, reproduced from the downloaded bytes, and that name is never recorded or exposed as a content digest.
- **The Cheat Script** discovery touches only its declared sitemap and bounded ranked posts, never its robots-disallowed search, category, tag or feed routes. Its Yandex public-resource key is an in-memory artifact identity, not a credential; transient download and storage URLs are never serialized, cached or logged. The API and first downloader hop use separate static exact-host policies. The downloader's current redirect is accepted without a third-party Referer only when its HTTPS host matches the bounded `s<token>.storage.yandex.net` grammar; that single returned hostname becomes the exact per-acquisition allowlist and still undergoes public-DNS, redirect and TLS validation. The API's advertised SHA-256 is checked against the downloaded bytes.

Direct and redirect response/staging sizes are bounded; cancellation removes partial files and is serialized with blocking import before shared staging is removed. Cache state excludes direct/signed URLs and password hints. Browser-selected files must remain under `DECKY_USER_HOME`, be regular/non-symlinked, and survive a stable-copy check before inspection. A provider page's advertised byte count may remain visible metadata; SHA-256, when advertised, is the integrity identity, while independent streaming and inspection bounds still reject oversized or invalid artifacts.

## Support bundle boundary

The support bundle is the one artifact CE Decky produces that is meant to be published, so what may enter it is an explicit allowlist rather than a filter. It is read-only, writes one file under `DECKY_USER_HOME`, refuses to write through a symlink at that path, and removes only archives matching its own name pattern. Environment capture is a fixed variable allowlist, never the process environment minus exclusions, so a variable nobody anticipated cannot leak; the count of omitted variables is reported instead. Panel log entries are revalidated on arrival with the same sensitive-field redaction and control-character stripping the backend log uses, and the archive carries no acquisition password, lock token, signed URL or credential of any kind, because none of those is written to the sources it collects. It deliberately does contain the user's game names and AppIDs, device paths, and the cheat tables their profiles select, since a table that fails to parse, load or enable cannot be diagnosed without it; the archive's own `README.txt`, the panel's help text and the project README all state this before the user attaches it, and the user removes what they do not want to publish. No Cheat Engine binary, installer or game file is collected. The system journal is the one source whose records are not this plugin's to begin with: every Decky plugin logs under the loader's single identifier, so the collector keeps a line only when the whole of its message is one it writes itself or one of the messages Decky writes about this plugin, each spelled out in full and matched to the end of the line. A component tag, this plugin's name occurring in a line, and an opening phrase Decky also uses are all message text another plugin can print, so none of them keeps a line on its own, and a loader message that is not written out is dropped and counted rather than published. The operator reads the rest from the device with `scripts/target_plugin_log.py --journal`.

## Cross-component validation

procfs records report a synthetic zero size, so every one of them is read through the descriptor-identity reader rather than the managed-file reader whose bytes-read/size equality check is what makes an in-place overwrite of a managed file detectable. The plugin-owned Cheat Engine launcher treats the live process table as untrusted corroboration: `/proc/<pid>/environ` is read bounded, parsed strictly, and used only to prove the game is running and to confirm an independently resolved compatibility prefix and an installed Proton identity. Linux may deny that file for a same-UID non-dumpable process; denial is never proof that the PID is foreign. When an exact durable runtime executable is known, readable `exe`/`cwd`/`cmdline` metadata may positively exclude an unrelated process, while a possible CE/Proton/Wine process or unclassifiable same-UID PID remains ambiguous. When malformed ownership has lost the executable identity, any such denial blocks controller repair; the record is quarantined only after a complete scan finds no syntactically valid CE Decky descriptor in any readable process. A running store launcher may be excluded from automatic game selection only by an exact known executable basename; its parent directory is not identity evidence because real games commonly live below the same tree. The prefix and Steam client root come from Steam library/tool metadata, every exact path component is rejected if it is a symlink or not a directory, an ambiguous or conflicting observation fails closed, and the launch environment is rebuilt from a base with every inherited `STEAM_COMPAT_*`, `PROTON_*`, `WINE*`, and Steam app variable removed. That base also undoes the dynamic-loader settings of the bundled interpreter CE Decky is launched by, restoring the `LD_LIBRARY_PATH_ORIG`/`LD_PRELOAD_ORIG` values it saved and unsetting the variables when it saved none, because everything the plugin executes is a system binary that must resolve the system's own libraries. Every process the plugin starts uses that base: Cheat Engine, 7-Zip, wineserver and the signature check alike. Decky does not reliably inherit the Game Mode display, so `DISPLAY` is accepted only from the Steam user's bounded, owned `gamescope-environment` and only when the corresponding X11 socket is live and owned by that user. Proton owns the launcher process group, but target evidence shows Wine clients can escape it; a bounded self-test therefore also retires and waits on the exact plugin-owned prefix through the selected Proton wineserver. Prefix-wide cleanup is forbidden for an attached launch because that prefix belongs to the running game, and an attached client is torn down by its exact descriptor instead. An attached launch is deliberately allowed to outlive a Decky reload so a running game is not disrupted; it is reclaimed afterwards only when the recorded PID's live environment still carries the exact `CE_DECKY_DESCRIPTOR` path and SHA-256, so a reused PID can never be signalled. A missing or reused PID clears the record as a confirmed exit, but an unreadable live PID or malformed record retains ownership and blocks another launch rather than guessing that the process is gone. A session replacement may skip the stale-heartbeat wait only when that owned group is proven gone and the last status write predates the confirmed exit.

Fail-closed checks apply across component boundaries, not only inside individual parsers. Runtime status cannot acknowledge generations absent from the replayable command log, duplicate positive result generations are rejected, and any still-retained issued command must be acknowledged with the same MemoryRecord ID; generation batches cannot skip ahead, frontend ACK matching independently binds generation plus expected MemoryRecord and descriptor/session identity, and a negative exact ACK remains an error while retaining its latest envelope for truthful UI state. Only typed `record_missing` may be handled as expected dynamic topology; target detachment and every other negative result abort before remembered profile state changes. A process target may change only through a retained acknowledged `retry_attach` command. Prepared sessions are marked stale if the selected table/consent/target process/imported CE identity changes, and runtime commands require a fresh current heartbeat. A fresh or clock-skewed observed heartbeat blocks current-session replacement/retirement; profile deletion is blocked while any prepared session is current. Process names and other UI-bound values reject bidi/invisible control characters. Persistent JSON uses bounded stable reads and rejects duplicate keys/non-finite values. Catalog enumeration is bounded before materialization, provider/game identity changes invalidate in-flight UI operations, and removal readiness fails closed for orphan/corrupt session state. Distribution ZIP creation is deterministic and rejects symlink inputs.

Target installation never derives its destination from a process command line or a conventional home path. The authenticated local Decky inventory must contain one enabled exact-name plugin and its version must match the backend status reached through that same name. The backend reports the exact `DECKY_PLUGIN_DIR` it received; the installer requires an absolute regular `plugins/CE-Decky` directory whose bounded regular `plugin.json` and `package.json` repeat the expected name and version. The one compatibility bridge for an older installed backend derives a sibling plugin path only from its exact Decky settings path and the upstream `DECKY_HOME/settings` plus `DECKY_HOME/plugins` contract, then applies every same check. A live mismatch is a conflict and never falls back. Only an unavailable live API may use the last verified bounded install record, which lives in per-user XDG state so clearing repository build output cannot erase it.

Off-target tests must not weaken the heartbeat freshness gate.

Revoke binds process stopping to the expected exact table and prepared session, with the supervisor checking the owned session before signaling. Its completion cannot clear a replacement ownership record. Failure epochs are advisory evidence ordering only: they can suppress an old success badge but never refuse table selection, consent, import or execution after the user clears Failed. Only a cause that says the table did not work commits one, and clearing such a record commits another in the same durable write, so the success it stood over stays in retest until a cheat proves the table again, including for a legacy record that carried no epoch of its own. A definite failure is never downgraded by a later payload or source record about the same bytes: only the user clearing it lifts it, while a definite failure may replace such a record and an unclassified one may still be refined by fresh structural proof. While a not-working record stands, one backend rule refuses a new association, selection or authorization of those exact bytes from every route, names the press that clears it and needs no network to satisfy; it never withdraws a selection or authorization that predates the record, never stops a running session, and never applies to source or payload conditions.

Positive evidence is validated by one strict current reader. It reads the shape immediately before the current one, which differs only by an optional field being absent, and states that field absent rather than guessing at it, so such a row supplies exactly the claims it already carried; every row then passes the same strict validation. No older or incomplete intermediate record is migrated, and a row this reader cannot read supplies no claim and no exception. A successful startup proof carries at most one ID independently of diagnostic history, chosen from the eligible records the descriptor states, bound to the current descriptor/session and checked against the same requested active leaves only after the entire startup completes. Summary rows cannot grant consent or override a failure epoch. Focus export discovery is independently bounded; resolving minimized-window restoration does not establish or disable focus capability.

Foreground fallback is allowed only when a call mechanism fails or returns no usable BOOL, never to override an operating-system refusal. The selected AppID supplied to status affects advisory fingerprint reads only and grants no launch identity or consent.

Autoload success evidence requires a record observed inactive immediately before its requested activation and active after settlement. Reassigning true to an already-active record, including one activated by table Lua or an enclosing script, cannot earn positive evidence.
