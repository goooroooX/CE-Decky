# Architecture

## System overview

`src/uiActions.ts` traces owned control callbacks without serializing event arguments and captures frontend interaction identity at operation entry. Its context ends when the synchronous handler returns, so unrelated background work cannot inherit it. `src/useUiSurface.ts` observes modal lifetimes; both write only through the existing bounded `supportLog.ts` ring and support-bundle collector. They do not change RPC arguments, execution consent or backend transaction ownership.

```text
Decky QAM frontend (TypeScript/React)
  ├── controller-only managed CE setup/progress/cancel
  ├── library item and AppDetails integration
  ├── compact current-game home plus Search/Review/Cheats/Advanced modals
  └── @decky/api callables
                  │
                  ▼
Decky backend (Python)
  ├── configuration and diagnostics
  ├── manifest-pinned CE download/native extraction plus CE/table import and immutable storage
  ├── profiles, per-game table-library/autoload state, and exact-SHA consent
  ├── private CE runtime materialization
  ├── session descriptor/control/status protocol
  ├── provider catalog/search/acquisition transactions
  └── on-target validation and provider diagnostics
                  │
                  ▼
DECKY_USER_HOME/.cheat-engine-decky
  ├── ce/installers/<artifact-sha>/
  ├── ce/installations/<artifact-sha>/
  ├── ce/runtime/<versioned-aggregate-runtime-sha>/
  ├── tables/sha256/...
  ├── state/profiles/...   (per-game table library, autoload, consent and cheat choices)
  ├── state/provider_sources.json   (the table sources this user switched off)
  └── state/sessions/<appid>/<uuid>/...

Starting Cheat Engine:
plugin-owned `proton runinprefix` launch into the running game's own prefix
  -> private Windows CE runtime in the game's Wine environment
  -> resident CE Lua bridge
  -> bridge loads the exact session table snapshot
  -> data-only descriptor/control/status files
  -> Decky QAM runtime controls
```

## Production boundaries

- `src/managedSetup.ts` owns one frontend setup observer from start receipt through terminal reconciliation. Cancellation interrupts its pending read and passes the exact result back to the same owner; it never creates a second completion consumer. Lost start, poll and cancellation replies are reconciled against backend capability. An active operation retains monitoring with capped backoff; a confirmed terminal result is not reversed by an optional refresh failure. Unmount releases the observer without cancelling the backend installation.
- Setup read deadlines apply only to capability, status and poll calls. Start, cancel and complete retain their actual mutation promises: neither a deadline nor observer closure cancels a Decky callable. Capability discovering another operation transfers observation to that exact ID, including after a terminal result; the old result never overwrites the newer operation. A failed new start cannot adopt the unchanged terminal ID that was already visible before the request.
- An operation missing from capability is reconciled through its exact idempotent completion RPC, never inferred from an installed path, a reinstall flag or prior handoffs. The owner caches the exact successful receipt through cancellation and completion handling. An unconsumed Cancel preempts ordinary reconciliation reads/backoff; a rejected Cancel receipt still requires backend reconciliation. Owner capability reads have no React publication side effects, so an abandoned read cannot restore stale setup state. A confirmed predecessor completion remains confirmed when observation moves to a successor.
- Review Stop state belongs to one activation attempt. Its completion checkpoints await that attempt's pending Stop, and only a confirmed stop rejects that activation. The panel also drains the attempt's Stop before releasing a failed activation; stale Review callbacks cannot stop a newer activation. Advisory status refreshes do not decide whether the stop RPC succeeded.
- `src/` owns Steam/Decky UI integration because SteamClient APIs are available in the frontend environment. It reads Steam identity (AppDetails, install folders, the shortcut store) and writes no Steam state at all.
- `py_modules/ce_decky/ce_launch.py` owns Cheat Engine process lifetime: exact prefix resolution, live game-container observation, corroborated Gamescope-display resolution, deterministic argv/environment planning, launcher process-group ownership, and isolated-prefix Wine cleanup for self-tests. It is the only component that starts Cheat Engine, and it never touches Steam state.
- `main.py` is a thin Decky entrypoint. It puts `py_modules/` and then
  `py_modules/vendor/` on `sys.path`, so the vendored distributions precede this
  plugin's own package. It then probes `xml.etree` and `html.parser`; when the
  Decky Loader PyInstaller runtime omits those pure-Python stdlib modules, it
  adds the verbatim CPython 3.11.7 `xml`, `html`, and `_markupbase` fallback
  under `py_modules/stdlib_fallback/` without shadowing a complete host stdlib.
- `py_modules/vendor/` is the plugin's third-party Python runtime, committed and
  shipped rather than installed. Nothing here authors it: it is the hash-pinned
  `requirements-runtime.lock` rendered by `scripts/update_runtime_vendor.py`,
  and its identity is the tree digest recorded beside that lock, which the
  repository rules check before anything is packaged. It is pure Python by
  construction, because a native artifact in it would be a binary this project
  ships without reviewing. It is committed because the official Decky Store
  builder copies `py_modules/` exactly as the repository holds it and has no
  dependency-install phase, so a tree produced at packaging time would reach
  this project's own archive and never the Store's.
- `py_modules/ce_decky/` owns filesystem state, validation, profiles, session preparation, runtime protocol, and diagnostics.
- `PluginService.get_status()` includes the exact `plugin_dir` Decky supplied beside its existing user/settings/runtime paths. The authenticated target installer uses that self-report only after the loader inventory and installed metadata agree on the same plugin identity and version; it is diagnostic authority, not a path the frontend may mutate.
- `py_modules/ce_decky/poll_counters.py` holds one process-wide monotonic count, with wall and per-thread processor time, for each repeating path a live session runs. Counts are taken at the RPC boundary for the two calls the panel's detector makes, and inside the launch module for the supervisor's scan and the process-table walk, so an internal caller such as the support bundle is not mistaken for the panel. `PluginService.get_poll_counters()` and its `get_poll_counters` RPC read the snapshot and increment nothing, which is why that RPC exists at all: reading through a counted path would make the reading one of the counts. It is the only RPC the frontend deliberately does not call, recorded as such in `tests/test_rpc_contract.py`, and the same snapshot reaches the support bundle inside `diagnostics_snapshot()`.
- `py_modules/ce_decky/managed_ce.py` owns managed Cheat Engine setup: reviewed-artifact and Proton-tool discovery, and the long-running native extraction transaction. The frontend supplies only an explicit reinstall boolean; it never supplies a URL, executable path, installer arguments, Proton identity, or output path.
- `dist/index.js` is committed build output consumed by Decky; `src/` remains its source of truth.

## Storage domains

Three path domains are intentionally separate:

1. `DECKY_PLUGIN_SETTINGS_DIR` for configuration.
2. `DECKY_PLUGIN_LOG_DIR` and `DECKY_PLUGIN_LOG` for Decky-managed logs.
3. `DECKY_USER_HOME/.cheat-engine-decky` for Proton-visible CE, tables, profiles, sessions, cache, and staging.

`DECKY_PLUGIN_RUNTIME_DIR` remains available for ordinary Decky runtime data, but Proton-consumed files use the managed user-home root so visibility follows Valve's home-sharing and Wine `Z:` behavior.

Provider identity is declared once in the provider registry in `providers.py`, which owns display name, rank, adapter kind, host allowlist, base URL, how the provider is reached and whether a download from it begins with a wait it serves out itself, per provider; `catalog.py` derives its host policy from that registry, and search jobs carry their provider with them rather than being matched to a separate list by position. A provider is reached either by a search of its own or only as the exact source another provider's page names, and the registry is what says which: the search's jobs, the per-source summary it returns and the query plan the panel shows are all built from that one answer, so a provider cannot be advertised as a source no search will ever query, and a provider declared searchable with no adapter behind it is reported as a failed source instead of being silently left out. Which of those providers this user actually wants used is a separate small durable store, `provider_sources.py` over `state/provider_sources.json`, kept beside the profile and blocklist stores rather than beside the provider diagnostics in `cache/`, because the cache is offered for deletion as a safe repair and a switched-off source coming back on by itself is not one. It records the providers the user switched **off** and never the ones left on, so a provider added by a later version is on for everyone who never expressed an opinion about it; an unreadable record reads as no refusals, exactly as an unreadable blocklist refuses nothing, and the reason reaches Advanced, the diagnostics snapshot and the support bundle instead of being swallowed. `catalog.py` consults it through a callable rather than a set captured at construction, so a choice written while the service is loaded takes effect at the next search, and it is applied at four points: the search jobs it builds, `_linked_source`, which is the route by which one provider's page names an exact page at another, the cached rows it re-serves, and `resolve`, the one funnel from a selected row to a download. One search runs against one answer: `search()` reads the choice once and publishes it in a context variable that `_linked_source` reads, so a switch pressed mid-search cannot change what that search follows while the roster still describes the selection it began with. Which providers another provider's page may name is declared in the registry as `linked_target` rather than inferred from `discovery`, because GitHub is both searched and linked while three of the five sources are searched and named by nobody; a linked read of a provider that does not declare it is refused as a defect. The frontend's own search cache carries a source-selection revision, because it is keyed by game and query alone: changing the choice forgets every stored outcome, and an answer that lands after the change is stamped with the revision it began under so it is not restored as current. The registry, not the selection, is what builds the search roster, which is what keeps a switched-off source in it as `disabled` rather than omitting it: an answer of no results otherwise cannot distinguish a narrowed search from a build without those sources. It is also the one place that says so, so nothing else in the outcome projects the same fact. The background listing crawl re-reads the selection on every page it owes and stops when its own source is switched off, because it outlives the search that started it by minutes and sleeps through provider cooldowns. Telemetry is attributed by the provider that answered rather than by the job that ran: rows and unreadable pages a linked read produced belong to the provider whose identity they carry, counted as a linked read rather than as a search of a provider no search queried. Deleting the provider cache suspends and drains interactive searches as well as the background listing crawl and downloads, so a search the user closed cannot finish afterwards and write back the files the deletion removed. A corrupt `providers.json` is not repaired by use, because every recording path loads it first and every caller ignores that failure so a broken counter cannot fail a search, so the store carries an explicit `reset()` that Advanced offers. Provider state is split between bounded cache/diagnostics under `cache/` and cancellable artifact staging under `tmp/provider-downloads/`; a diagnostic row whose provider is absent from the current registry is returned only as explicitly retired history. Catalog results expose opaque provider artifact IDs; direct URLs remain backend-only and are not persisted in stale cache state. Artifact-specific browser handoff watches a bounded `DECKY_USER_HOME/Downloads` snapshot and copies a stable regular file into managed staging before validation. A challenged provider search has no trustworthy filename or size, so its backend-owned action disables automatic detection and requires an explicit Decky picker result under `DECKY_USER_HOME`; the selected basename then replaces the action placeholder in inspection and provenance metadata.

`artifact_resolutions.py` stores at most 4096 verified `(provider, artifact_id, artifact_sha256) -> table_sha256` resolutions in `state/artifact_resolutions.json`. Acquisition records only a structurally valid direct CT or an archive with exactly one CT candidate, after verifying the advertised artifact SHA. A refused cheat may still establish that identity; damaged content cannot. The cache contains no URL and supplies provenance only. Clearing a failure changes no resolution, and the resolution refuses nothing by itself.

`table_compatibility.py` stores at most 4096 successful `(app_id, table_sha256)` observations in `state/table_compatibility.json`, separate from consent and the negative blocklist. The service holds bounded pending activation generations in memory, observes the exact successful ACK and a later issued query returning active, and persists when `confirm_table_working` finalizes the successful frontend operation or the backend observes complete successful startup leaf readback from the separate single-ID startup proof, independent of the 128-result diagnostic history. Enclosing scripts are excluded when a requested descendant was also enabled. Backend reload discards unfinished proof. Evidence records the observed target basename, optional PE version, optional Steam build ID, the absolute path that fingerprint was read from, success time and invalidation state. The path is what makes a record comparable after the game stops: the PE version is read from the running game's own executable and a non-Steam shortcut has no build ID at all, so without it a shortcut's proven table had nothing comparable the moment it closed. It is knowable only while the evidence is being recorded, is validated as an absolute path like every other stored string here, and is absent from a record written before it existed, which compares exactly as it did. The target basename is required data validated exactly as a profile validates one, because every comparison against the current profile turns on it; a row without a usable one makes the whole store unreadable, which is a bounded reason and an empty claim rather than a failed status call. Steam build identity is read from one unambiguous AppState manifest under the existing Steam-library discovery authority. Any comparable mismatch requires retest; at least one comparable match and no mismatch permits green; no comparable signal remains neutral. Negative evidence commits a failure epoch with the refusal, and only for a cause that says the table did not work, because a payload or source record answers nothing the positive store holds; it commits independently of positive-store invalidation; clearing the refusal cannot restore earlier success. Both new state files are collected within the existing support-bundle budgets; unreadable records supply no identity or success claim.

`activity_log.py` is the shared log-safety formatter and `OperationRegistry` is the outer asynchronous operation observer. Every registered backend operation logs start and terminal state with a short correlation ID and duration; names come from fixed call sites rather than caller input. High-frequency successful reads/polls are debug-only unless slow. `StateTransitionLog` covers the two facts that are polled rather than called: the runtime envelope, whose attach, PID, target, table-load, startup, window/dialog and last-failed-result state is written once per change and never per poll, and table inspection, written once per digest. Both keep fast-moving counters out of the change signature while still reporting them, and a deleted profile forgets its runtime key so the next game at that AppID is recorded again. Catalog/acquisition, managed setup, runtime materialization and CE launch add domain phase events at the point where they can name the failing boundary. Expected domain/input errors are bounded warnings. Unexpected exceptions are bounded errors with sanitized traceback frame identities, never locals or arbitrary request/response data. These observers retain the component's original error/state contract and re-raise when the caller owns the failure. HTTP client request logging is raised to warning so dependency internals cannot duplicate signed URLs into the ordinary plugin log.

`support_bundle.py` is the read-only collector behind **Advanced -> Report a problem**. The service reads every backend snapshot itself and passes them in, so a probe that raises becomes a manifest note rather than the reason a user has nothing to attach; the module owns only file collection and archive shape. It walks Decky's plugin log directory, `state/ce-launch/`, the settings/profile/blocklist/source-selection/provider-diagnostics files, bounded newest session and self-test directories, and the cheat tables the profiles currently select, then writes one deterministic ZIP under `DECKY_USER_HOME` and prunes all but the newest five it wrote. Every read is bounded, refuses symlinks, and truncates rather than refusing: log members keep their tail, state members their head, and a per-member plus whole-bundle byte budget bounds the result. Session `table.ct` snapshots are excluded because the same bytes are collected once by digest. The frontend's bounded ring buffer arrives as an RPC argument and is revalidated entry by entry before it is written.

The panel keeps that ring buffer in `supportLog.ts`: bounded, in memory, never persisted, read only when a bundle is collected. `runAction` records every user-triggered action and its outcome, a React error boundary inside Decky's own records a render crash before rethrowing to it, and modal opens, game hydration, launch and stop record their identities. Field names matching the backend's sensitive-field pattern are recorded as present rather than by value.

The public acquisition state distinguishes `waiting_provider` from byte transfer. Only the remaining bounded countdown is exposed; transient tokens and URLs remain inside the backend task. A provider whose own chain makes the user wait before any byte moves declares `serves_download_wait` in the registry, and a download from it presents that state in a separate owned modal which continues through optional archive selection/password and import. Playground and VGTimes both declare it, for a countdown their own client contract enforces and, at VGTimes, a one-download-at-a-time rule that queues the second acquisition behind the first. The catalog screen reads that flag off the acquisition it just started rather than recognising a provider ID by name, which is how the second provider with exactly that chain came to be added without the modal; an acquisition whose provider this build no longer declares reads as no wait rather than failing the poll of a running download. the ordinary single unencrypted CT path auto-imports, while even one encrypted archive member requires password input. Closing/unmounting the modal cancels any nonterminal acquisition, and closing a failed completion preserves its diagnostic while still retiring retained staging. Each acquisition serializes its blocking completion and cleanup under one mutation lock, so cancellation either wins and removes staging before import starts or observes the terminal imported result after import finishes; it cannot unlink the source beneath `TableStore`.

What each source's adapter owns on top of that registry and the shared transport, one source per entry:

- **FearLess** is indexed rather than queried, and `fearless-index.json` is a resumable bounded map of forum page offsets to topic IDs/titles only. Page zero establishes its multi-page stride through numeric page-number/offset relations and advertised totals, while a one-page index carries only offset zero and a null stride. A later page may omit independent stride evidence and reuse that proven geometry, but its page number and totals must fit and any explicit stride must agree. Search refreshes page zero before deriving other leading offsets, resumes missing listing pages through one background task, atomically checkpoints bounded batches, and fetches topic pages only after local ranking; unload cancels the crawl and drains any in-flight cache write before shared HTTP closes. When Search was last used is what arms that background pass for a day, and it is durable in two places: inside the index cache, where an ordinary write carries it at no cost, and in `fearless-search.json` beside it, which is a few dozen bytes and has no second writer. A search writes the small one as it happens, because it takes no lock and costs nothing, and the index cache carries the same value whenever a crawl next writes it; load takes the newer of the two. The unload prologue and the background scheduler write only the small one as well, and by then there is normally nothing owed: what they exist for is the search whose own write failed on a device that was full for that moment. Both live in the cache directory, so deleting the provider cache removes the arming with the index it is about.
- **Playground** carries no link until a download starts: its records retain only bounded in-memory file/post identity; acquisition exchanges it for a one-use countdown token and temporary CDN URL, then discards both after the shared downloader starts.
- **VGTimes** owns its whole download chain in `vgtimes.py`, which holds parsing and arithmetic and no network of its own: the catalog service makes every request, so the chain is exercised offline from a captured challenge. Its acquisition request is the one place that sequences those requests, and it returns the exact per-acquisition host policy the page declared alongside the link. The transport grew one form-encoded POST for it, sent once and never redirected, because a POST is not safely repeatable and where a redirected one would go is the caller's decision. `aes_cbc.py` is a decrypt-only pure-Python AES-CBC so that reading one provider's challenge needs no native wheel per architecture. The acquisition manager serializes the downloads of any provider whose request declares that it is served one at a time, which is a property of the request rather than a provider name in the manager.
- **GitHub** carries two routes into the same adapter: a search of the repository index, and the exact repository another catalog's page names. Both end in the same reader, which takes a repository's releases first and its tree only when the releases carry no table. Discovery, ranking and route construction live in `github_discovery.py` and hold no network of their own; the catalog service owns every request, and one shared helper turns an exhausted anonymous budget into the provider cooldown the acquisition layer already waits out. `cache/github-repository-index.json` keeps at most 32 normalized answers keyed by exact query: a one-day fresh answer skips only the scarce repository-index request, and an answer no older than seven days may replace that request only when refresh is unavailable. Release and tree reads are never served from it. A committed table carries a git object name on the artifact record, verified in the acquisition worker beside the SHA-256 check and never exposed through the record's public form.
- **The Cheat Script** ranks its declared sitemap locally, retains only a Yandex public-resource key for each selected row, and asks the anonymous public API for exact metadata during search and a transient link during acquisition. Its request strategy consumes the trusted downloader's one redirect without a third-party Referer, validates the Yandex storage-shard hostname grammar, and returns the one exact runtime host to the shared downloader. Neither transient URL is serialized or cached.

Managed CE setup follows the staged long-transaction model rechecked against Decky Wine Cellar `3445b50f`: backend-owned operation state, bounded download, native format validation/extraction, cancellation, validation before promotion, and no in-place replacement of an installed payload. Extraction writes only to the per-operation owned staging tree; cancellation drains its worker before cleanup, promotion is separately drained across its commit point, and every terminal path removes that exact UUID work tree only after both workers are gone. If cancellation arrives after promotion commits, backend and frontend preserve `completed`, register the exact identity and report the truthful outcome. The service holds a mutation reservation across the whole asynchronous setup, beginning before manager start can publish an operation ID and ending only on failure/cancellation or after the completed installation identity is persisted and the operation is consumed. Session preparation, private-runtime materialization, CE import/clear, launch/autoload and other identity-dependent workflow therefore fail closed instead of racing promotion. The frontend automatically reattaches its monitor to the one surviving operation after reload rather than exposing a second resume/start transition. Because Decky can temporarily retain overlapping observers, the service keeps one in-memory exact-operation completion receipt until the next setup starts: a duplicate completion is read-only and marked as already committed, while a poll of the consumed operation reports it as unknown so a superseded frontend monitor cannot repaint terminal setup progress, and every different or stale operation ID still fails closed. Service unload attempts every subsystem close in dependency order and re-raises the first failure only after the remaining bounded owners have drained. No Proton process, prefix, journal, installer argument or installer execution belongs to setup.


## Managed/imported CE and private runtime

The manifest-pinned managed installation or manually imported fallback is read-only source input after registration. CE Decky records the executable path and SHA, then fingerprints the complete source tree when materializing a runtime. The bridge and deterministic early-load bootstrap are added only to the private copy. Runtime directory identity is:

```text
(CE executable SHA-256, complete source-tree SHA-256, bridge SHA-256)
```

The physical directory uses one versioned aggregate SHA-256 of that tuple so Wine's `steam.exe` proxy does not cross its legacy path limit; the manifest retains the tuple. The source `main.lua` is preserved byte-for-byte under a reserved runtime name, while a generated `main.lua` loads the exact bridge before the preserved source and CE's unordered autorun enumeration. Existing immutable runtimes are reused only after full validation. Damage or identity mismatch fails closed; the directory is not repaired in place. CE bytes never enter Git or the plugin package.

## Table storage and session snapshots

Imported tables are stored by exact SHA-256. Imports durably publish catalogue metadata before blob promotion, so an interruption leaves a named unavailable entry rather than unlisted bytes. No metadata-failure rollback removes a pre-existing blob. At initialization, under the service mutation lock, `TableStore.reconcile_orphan_blobs` scans at most 256 shards and 10,000 entries and reads at most 128 MiB of candidate data. It recreates metadata only for exact-SHA validated CT blobs that have no metadata entry, preserving existing records and all blob bytes. Recovered filenames identify the digest; origin and arrival remain unknown. Recovery and refusals are logged in the ordinary backend log collected by the support bundle. Unprocessed entries remain for the next startup; no status read performs reconciliation. Provenance and profile state are separate from immutable bytes. A game profile may additionally retain a bounded `table_library` of exact SHA associations, an `autoload_enabled` flag, and exact-SHA remembered runtime preferences. Those fields never rename, copy, or weaken the immutable table store. Session preparation re-verifies the stored table and creates a session-local snapshot so execution consent and runtime identity cover the bytes actually passed to CE.

While a session is live the backend runs two repeating things and nothing else: a one-second tick that asks whether anything recorded at launch still proves the game alive, and a three-second target check. The panel's own detector is a third cadence, but it is the frontend's, it calls the backend only for a selected game, and it makes no call at all while the quick access panel is hidden. Each of these paths carries a monotonic counter and its per-thread processor time in `py_modules/ce_decky/poll_counters.py`, which is what makes the cost of a session attributable to a loop rather than to the process.

The one-second check stops at the first PID that answers alive or unreadable, and offers that PID back to the next tick as a starting point; the predicate is unchanged and proving the game gone still reads the whole set. The three-second check, once a complete scan has named the target, confirms that one process by its PID, start time, declared Windows executable and declared AppID instead of walking the table again. That cheap path may only ever answer `present`. A start time that moved, an executable that changed, an environment procfs will not hand over, or a PID that is gone all fall through to the complete scan, and an identity is dropped the moment a scan stops confirming it. An unreadable target is the one case the fallback cannot resolve either, because the scan skips exactly the processes it cannot read, so it reports `unknown` and keeps the identity rather than reporting an absence it has not proved.

The capability path is separate and is not part of that cost, because it does not run while the panel is hidden. It is heavier than a status read: one refresh observes the game container, enumerates and hashes the installed Proton tools, observes the container a second time for Proton matching, checks ownership and recovery records, and hashes the registered Cheat Engine executable. Three things follow that are deferred rather than done, and are recorded here so they are not rediscovered: one trustworthy container observation should feed both uses instead of two; the Proton and Cheat Engine hashes are static identities being recomputed for a display refresh and could be cached against explicit filesystem identity; and a light display capability could be separated from execution validation, which must keep revalidating exactly as it does at the launch and mutation boundary. All three are panel responsiveness rather than session cost.

An attached Cheat Engine is a client of the game's own Wine session, because that is what lets it read the game's memory. Its liveness supervision therefore cannot be the game's process set: those processes report the game's AppID and outlive the game for as long as Cheat Engine holds the prefix open. Supervision watches the exact target process the session was prepared for, and only a complete process-table scan may prove it absent. The durable launch record (schema 5) carries that target, and records that the target was actually observed alive, so supervision regained after a plugin reload applies the same rule without having to see the game a second time first; a record written before it keeps the older baseline-only behaviour. The process set observed when the launch started is startup context, never proof the game left: a game started through a launcher replaces that whole set during an ordinary handoff, so where a target is known only its scan may end the launch, and the baseline having gone is what makes that scan happen immediately.

Table metadata schema 3 records when bytes first arrived on this device, and every route that rewrites a record writes that same marker: the schema a file claims has to be the schema it is, whatever the reader is willing to tolerate. Removing a table removes and syncs its bytes first and its record last, because a record whose blob is gone lists as a table whose file is missing and can be acted on, while a blob whose record is gone is storage nothing can name, reach or remove; each step repeats safely, so a removal that failed part way is finished by pressing again, and the path to those bytes is walked from the store's own root with every component required to be a directory this store owns, so a link anywhere along it is refused rather than followed and a link at the file itself is unlinked as the entry it is.  A downloaded table already carried the date in its origin's `retrieved_at`; a table opened from a file has no origin, so a stored list could date only half of itself. The stamp is written by the promotion that first stores the bytes and carried forward by any later import of the same file, because a second copy of one table is not a second arrival, and a record written before this was tracked has none rather than being given a file timestamp. The exact-SHA Revoke command retires the safely stopped session and delegates consent withdrawal, Auto-load disarming and detachment to one ProfileStore save. It retains bytes and unauthorized history, requires no installed-game lookup, and refuses a changed selection. Profile schema 5 keeps current-table startup/pins/consent/remembered state, the user's own configured values, and bounded history by exact SHA. Loading schema 1-3 derives the logical table library from already persisted current/previous/history SHA identities; schema 4 promotes the typed values it kept inside remembered state into configured values, discarding blank and unreadable-placeholder answers that were never a user choice; saving rewrites through the normal atomic profile store. Autoload uses remembered state only after an exact table/profile match and never performs cross-SHA MemoryRecord remapping. The previous-table pointer records the selection a game came from and survives that selection being cleared, so a table taken away can be chosen again without hunting for it; selecting the table it names leaves the game with nothing to go back to, because a pointer at the current table is not a previous selection and no read of the profile would accept one.

Remembered state and configured values are separate layers for the same MemoryRecord IDs. Remembered state is a reconciliation of a live session and may legitimately change to whatever Cheat Engine last reported; a configured value is the number the user chose and is written only by the picker's Apply. Where both exist for one record, the configured value supplies the value and remembered supplies the active state.

Each prepared session has a unique AppID/UUID directory containing:

- `descriptor.txt`: immutable data-only session description;
- `control.txt`: backend-owned generation log;
- `status.txt`: bridge-owned heartbeat, typed command results and optional bounded table-load diagnostics (AddressList count plus exact descriptor-path match);
- `table.ct`: exact verified session snapshot;
- `session.json`: host metadata and identity.

The transport is parsed data, not Lua source. Mutable files are never evaluated.

The diagnostic status fields and result error codes are optional so an updated backend can still read a surviving legacy bridge heartbeat. A typed `record_missing` is the only negative record result the frontend may model as per-record unavailability; an untyped legacy failure and every operational code remain fatal. These fields do not authorize a table or MemoryRecord; target tooling uses them only to distinguish a table-load failure from an exact-ID lookup failure after the descriptor/table identities have already matched.

`atomic.py` owns the shared durable rename/unlink contract. Post-mutation directory-sync errors retain the `DurabilityUnknownError` type across repair and ownership boundaries. Quarantining profiles also preserves that outcome when creating the empty replacement fails. Bulk cleanup reports directory-sync failure in its per-scope result instead of claiming successful durable removal.

## Steam state boundary

CE Decky does not own Steam state, and there is no code path that could. The frontend reads AppDetails, install folders and the shortcut store for identity; `game_files.py` answers which Windows executable one installed game starts, read only and bounded, resolved through the same library discovery every other Steam read here uses. `steam_launch.py` reads Steam's own `appcache/appinfo.vdf` for that: the client's launch entries for the AppID, filtered to Windows, to the branch the game's `appmanifest` says is installed, and away from entries conditioned on downloadable content whose ownership this cannot prove. It skips every other app by the length Steam wrote in front of it rather than loading the cache, and reports a stated reason rather than an empty list. What that record names is resolved under the game's own install directory and reported only where the file is there; where it answers nothing, the bounded walk of that directory is what is listed instead. It refuses a manifest that names another AppID, an install directory that is not one name under that library's `steamapps/common`, and any symlink out of the game's folder; the same AppID under two libraries is a stated refusal rather than a choice between them, because the wrong one names a different build of the game. The backend starts Cheat Engine itself as an owned POSIX process group in the running game's prefix. Nothing writes launch options, `shortcuts.vdf` or `localconfig.vdf`.

An earlier design did the opposite: it wrote a Proton sidecar command into the game's Steam launch options and carried a durable `profile.launch_ownership` write-ahead recovery journal so a crash could not leave that write unowned. 0.9.0 deleted the whole integration - the launch-option parser/editor, the ownership journal, the `shortcuts.vdf` writer and the two recovery RPCs - because the attached launch replaced it. Profiles written by an earlier version still load; a non-null legacy `launch_ownership` value is rejected rather than silently discarded, because this build could no longer restore what it describes.

## Integration stability tiers

1. **Decky-supported:** callables/events, lifecycle, environment paths, logging, and file picker.
2. **Typed SteamClient with current plugin precedent:** AppDetails, system browser/explorer, game-action and suspend/resume notifications. Centralize and target-test these wrappers.
3. **Private Steam surfaces:** React context-menu anchors, BrowserView, and CEF/CDP. These are optional and cannot be required for core operation.

Foreground recovery remains inside the resident bridge. Attach, suppressed dialogs/forms and completed cheat interaction coalesce into one bounded sweep budget. The bridge resolves its own `user32` exports before attach, enumerates top-level exact-PID windows, requires one visible non-minimized candidate, requests `SetForegroundWindow`, and counts success only after foreground readback names that handle. `focus_candidates`, `focus_attempts`, `focus_successes` and `focus_reason` are optional strict status fields collected with session status and logged on transitions. The existing minimized-window restore and application notification retain separate counters.

Compatibility status batches executable observation into one bounded process scan and discovers Steam libraries once per snapshot. Only apps with an observed current executable and the explicit current AppID get a manifest read; other inactive historical apps remain unknown. The frontend passes the selected AppID to status and refreshes after selection, so a stopped selected game retains its independent Steam build comparison. Unreadable profiles provide no fingerprint; a changed target executable never inherits a match from the game's build ID. Startup preparation retains only exact-session requested active leaf identities in backend memory. An applied startup with complete progress and successful generation-zero active readback can finalize that proof; submission, enclosing scripts alone, rollback and a replaced session cannot.

Negative evidence and its per-digest failure epoch commit together in `state/blocked_tables.json`. A record carries the release the source advertised for those exact bytes, because the record outlives the file it is about: one post carries every revision of a table under one filename and one title, so a list read months later has nothing else to tell two of its own rows apart. It is the advertised release only, never the `.CT` file's own `CheatEngineTableVersion`, which is the version of Cheat Engine's table format; where no source stated one the field is absent and the panel reads it from a copy still on the device. The list is bounded at 512 rows and makes room from the records a download or a source left, oldest of those first; a record that a table did not work is never evicted to admit one, and a list holding nothing else refuses the new record with the press that makes room, because eviction must not become a clear the user never made. One origin-retention policy covers every write, including a bulk repair of a record that has none: submissions are validated and de-duplicated in the order they were recorded and the newest eight rows are kept, so the row the bytes were most recently found through is the row that carries the mark. Recording a failed cheat invalidates that table's positive evidence before the negative record is written, because the cheat did not work whether or not the bounded list had room for the row; a refusal for capacity reaches the user with the press that makes room in it. A repair that recovers a record's lost provider rows reports the rows the record kept rather than the recovery it was offered, so the first read after it and every read after that describe the same set. A write that raises after its replacement is already visible is reconciled the same way the rest of this backend treats post-commit uncertainty: the record on disk is re-read and reported, and only a record that cannot be read at all falls back to what the repair recovered. Up to 4096 epochs survive clearing advisory rows; eviction rotates a default token so forgotten failures cannot revive earlier success. Positive records carry the epoch they observed. Compatibility schema 3 requires every field, including an explicit 32-hex failure epoch and the absolute path the fingerprint was read from, which is `null` where no route saw one. Each of these two stores also reads the one shape before its current one, because in both cases that shape is the current one with a single optional field absent - the advertised release on a negative record, the executable path on a positive one - and the next write puts the file in the current shape. A row so read carries exactly the claims it carried and no more. Anything older, and any row this reader refuses, supplies no claim and is replaced by the next confirmed success. The clean missing blocklist has a stable all-zero initial floor; current blocklist reads validate both rows and epoch metadata, including an empty record. Unreadable history or a different epoch disqualifies green independently of best-effort invalidation writes. The existing support collector includes both files within its unchanged budgets.

Revoke's stop carries the expected table SHA. The backend validates the selected table and captures its prepared session before asking the supervisor to stop only that session's operation or recovered ownership record. Manage confirmations carry holder AppIDs separately from bounded display labels; refreshed confirmations use refreshed identities, and stale holders cannot prevent processing later confirmed holders.

Focus capability discovery has its own 20-sweep budget, independent of minimized-window restore discovery. Missing focus exports do not spend the activation budget. Status includes the discovery count and at most one successful startup active ID as an `S` row; the service intersects those IDs with backend-prepared active leaves only after complete successful startup. Value-only and off descendants do not shadow an enabled ancestor. Support bundles collect the complete status under existing file and archive limits.

Focus calls prove and cache their local-call route separately for visibility and foreground activation. A missing, throwing or unusable `executeCodeLocalEx` result permits the one-parameter `executeCodeLocal` route; a valid false BOOL never does. Bounded `focus_capability` and `focus_error` fields preserve the proven routes and last error in status, transition logs and support bundles.

The startup descriptor states which requested active-on actions could prove the table works: those with no requested active-on action of the same plan nested inside them. The bridge cannot derive this, because it never sees the record tree the paths come from and a nested record does not exist until the script above it has run. It retains successful readback for the first of those records to be observed transitioning inactive-to-active, independently of the result ring, so a plan whose deepest eligible record was already active still proves itself through one that was not. Async startup carries the pre-action eligibility until settlement; an already-active record or value-only readback provides no proof. The backend still intersects it with prepared active leaves and requires complete successful startup. Pending proof is consumed only on durable evidence persistence or definitive disqualification; transient I/O leaves it retryable. Recurring proof size is independent of startup-plan length. Blocklist mutations use the atomic writer as their sole directory durability boundary.

Manual activation returns both whether compatibility confirmation succeeded and whether it may have changed anything, which are different answers: a confirmation that reports an unprovable durability may already have committed the evidence. Picker and pinned controls refresh advisory status for either, before independent preference writes or further reads can fail. A manual start observes startup to a terminal state through the same bounded poll auto-load uses and then rereads status, because startup proof is persisted by the status read that observes it and can settle seconds after the bridge answers; both the observation and the reread are advisory and never turn a running Cheat Engine into a failed start. A failed advisory refresh is logged without replacing a later persistence error. Compatibility compares Windows process basenames case-insensitively while preserving original spelling for display and diagnostics; a spelling-only profile change does not represent a new executable.
