# CE Decky Design

## 1. Product definition

CE Decky is a Decky Loader plugin for SteamOS that manages Cheat Engine tables per Steam library item. Its primary first-run path downloads one reviewed official Windows Cheat Engine artifact, verifies its exact release-manifest SHA-256, extracts its reviewed payload natively without executing the installer, and registers the validated plugin-owned tree. After explicit compatibility validation, it launches that managed installation (or a controller-imported fallback installation) through the selected game's Proton environment and exposes selected table controls through Decky's Quick Access Menu.

The first stable release targets Windows games running through Proton, including eligible non-Steam shortcuts. Native Linux games remain searchable and manageable, but the Windows Cheat Engine launch integration is unavailable when Proton cannot be proven.

## 2. Product goals

Stable v1 should let a user complete this workflow in Game Mode:

1. Download, verify, and install the reviewed Windows Cheat Engine build from QAM; importing an existing installation is a fallback.
2. Select a Steam game or non-Steam shortcut.
3. Import a local `.CT` file or acquire one from an enabled provider.
4. Inspect the table without executing it and explicitly select the exact table SHA.
5. Choose startup actions, pinned controls, and a target process.
6. Start Cheat Engine from the panel while the game is running, as a plugin-owned process in that game's Proton environment.
7. Use QAM controls for supported `MemoryRecord.Active`, `MemoryRecord.Value`, dropdown, query, process-list, and retry-attach operations. Asynchronous script activation remains pending while CE reports `AsyncProcessing`, settles on a bounded timeout, and completes before dependent controls run; a failed mutation reconciles live state without removing the pinned controls from Home.
8. Apply table/version changes made during gameplay on the next launch.
9. Stop Cheat Engine, or prepare for removal, without touching Steam state at all.

Every production step above must be controller-usable in Steam Game Mode. Desktop Mode, terminal commands, manual path editing, and the target harness are validation/development tools, never normal user prerequisites. A provider that requires browser challenge handling is skipped, not handed to the user: browsing the web with a controller is not a workflow, so a challenged provider is reported with its own visible result count and the workflow continues with the sources CE Decky can download itself, plus local file import.

Stable v1 must support paths with spaces and Unicode, Steam and non-Steam library items, multiple immutable table versions, plugin reload, and rollback to a previously selected table SHA.

## 3. Non-goals

Stable v1 does not:

- bypass, disable, or hide from anti-cheat systems;
- bundle, republish, or patch Cheat Engine;
- execute a table merely because it was imported or downloaded;
- perform memory scanning itself;
- write Steam launch options or any other Steam configuration;
- hot-switch a table inside a running Cheat Engine process;
- remap MemoryRecord IDs across different table SHAs;
- require private Steam BrowserView or CDP behavior;
- run a native Linux Cheat Engine build as its runtime;
- integrate with Steam's own context menus, whose private Steam UI compatibility is not proven;
- execute the official page's download helper, or install an artifact that matches neither the reviewed SHA-256 nor the reviewed publisher key.

The expected use case is offline and single-player gameplay. The user remains responsible for the game and table source terms.

## 4. Reuse-first implementation strategy

CE Decky should reuse known working mechanisms from current Decky, SteamOS, Proton, and Cheat Engine projects wherever licenses and trust boundaries permit. “Reuse” can mean direct adaptation with attribution, a small compatible subset, or behavioral precedent. It never means importing another repository wholesale or treating a private surface as stable.

| Area | Primary reference | Mechanism to reuse | CE Decky-specific work |
|---|---|---|---|
| Decky layout and lifecycle | Decky plugin template and Decky Loader | `main.py`, `py_modules`, API-v1 lifecycle, environment paths, logging, file picker | Track owned tasks; make unload honest; keep uninstall non-destructive |
| Frontend build | `@decky/rollup`, `@decky/api`, `@decky/ui` | Official `src/index.tsx` to `dist/index.js` convention and Decky-native controls | Pin the supported toolchain and commit the bundle |
| Steam app and shortcut identity | CheatDeck and decky-proton-launch | AppDetails subscription for display name, compatibility tool and shortcut executable | Read only; verify exact AppID identity on every observation |
| Native CE 7.7 extraction | Project-owned `tools/ce77_extract.py` | CE-specific Inno loader/CRC/metadata/payload checks without executing the installer | Adapt the parser into the backend, keep the standalone tool for future artifact investigation, and retain manifest/tree/promotion trust boundaries |
| Owned Cheat Engine launch | Valve Proton `run`/`runinprefix` verbs | Full prefix setup for an owned prefix; `init_session(update_prefix_files=False)` plus `run_proc([wine_bin] + argv)` for a running game's prefix, the same invocation Proton uses for its own sidecar | Own the POSIX process group, resolve the prefix independently, observe the running game's Proton identity, and require a bridge heartbeat |
| Long artifact transactions | Decky Wine Cellar | Bounded download, staging, cancellation, validation, atomic promotion, rollback | Reimplement the transaction in Python with CE Decky limits |
| Artifact identity | Decky Framegen and release manifests | Explicit artifact version/name/SHA metadata | Treat SHA-256 as identity, never display version alone |
| QAM controls | Decky-Speedhack and current Decky UI | Toggle, value, dropdown, modal, progress, and per-game QAM patterns | Bind controls to exact table SHA and bridge results |
| Game lifecycle UI | OpenSave and current Decky types | Lifetime events, backend events, cleanup on dismount | Treat Steam events as hints; bridge heartbeat is authoritative |
| Game enumeration and persistence | decky-proton-launch | Steam manifests, non-Steam shortcuts, backend-persisted state | Enrich with AppDetails and never guess an AppID |
| Optional controlled browser | DeckWebBrowser | BrowserView/CDP feasibility | Post-v1 capability only; the controller-accessible file picker is the fallback |
| Same-environment helper precedent | Faugus Launcher | Additional application in the game's compatibility environment | Corroborating evidence only; Valve's sidecar is authoritative on Steam |
| CE startup and Lua APIs | public Cheat Engine source and `celua.txt` | `.CT` argv load, autorun ordering, process and MemoryRecord API names | Behavioral evidence only; exact CE binary SHA must pass target probes |
| Host archive tool | SteamOS/Arch 7-Zip package | Existing `7z`/`7za`/`7zr` CLI | Discover once, use absolute argv, enforce pre/post extraction bounds |

Every reused mechanism records its origin with the code that adapts it: the upstream repository, the exact commit or tag, the path, and whether the code was copied, adapted, or used only as behavioral evidence. Licensing and attribution obligations are recorded in `defaults/THIRD_PARTY_NOTICES.md`.

### Reuse rules

1. Prefer the current pinned mechanism over tutorials or recalled API behavior.
2. Inspect the upstream license before copying code.
3. Preserve attribution in source and `defaults/THIRD_PARTY_NOTICES.md` where required.
4. Copy or adapt the smallest coherent unit that preserves the proven behavior.
5. Add regression tests for every behavior relied upon.
6. Do not copy known weaknesses: partial VDF parsing, guessed AppIDs, hard-coded home paths, unchecked writes, or private UI dependencies.

## 5. User experience

### How a paged screen fits the display it is on

Every screen here that lists rows a page at a time fits that page to the display rather than to a number chosen once. Three facts about Game Mode decide it, all measured and all recorded in `docs/FIELD_NOTES.md`: Steam draws a modal inside a box that is the usable page, it adds its own padding above and below the plugin's content inside that box, and it paints a bar along the bottom of the page over whatever is behind it. That padding is Steam's and stays Steam's: pulling a window into it with a negative margin was tried on a device and is not available, because a window that overflows its own box then reports itself as hiding content and the correction below eats the page chasing it.

Before any of that, a short screen is drawn in a smaller hand. Giving a page a row fewer is not fitting a screen to a display, so on a handheld the heading, the two lines a row is set in, the gap between one cheat and the next, the padding Steam's own dropdowns and text boxes take when nobody sizes them, and the row a paged screen ends with are all tightened together, in one media query against the page the plugin's DOM is actually rendered in. Two screens also say the same thing in fewer lines there: Configure cheats puts its counts on the line above rather than under it, and the sentence explaining a stored-only selection goes behind the question mark that row already carries. Nothing is dropped and nothing moves on a television, which is the screen this plugin was built for and the one that has the height.

The page size is then arithmetic followed by a correction, and the two have different jobs. The arithmetic reads what is above the list and what is below it and divides what is left by a measured row; it is taken while the screen is being laid out, so it can be a measurement of a layout the reader never settles on, and it has been wrong in both directions on a real device. The correction asks the box the window is drawn in what it is keeping out of sight, which is the one statement here that rests on nothing, and gives up exactly that many whole rows. What is left under a footer inside that box is deliberately never read as room, because Steam's own padding is in there with it.

Shrinking has the last word. A screen drawn behind the bar is a failure and a screen with a row of room it did not take is a cost, so a page may grow once, only before it has shrunk, and only while the list has more rows than the page is showing; it may shrink while the box is still hiding something, up to a small bound. The bound is what stops a screen whose own chrome is taller than the display from being paged down to nothing in pursuit of a fit that paging cannot reach.

### What a row says first

A row is cut to one line until it is opened, so the order of a message is what decides whether the reader gets the finding at all. Every composed message leads with the specific cause and follows it with CE Decky's own framing and the next step: `<cause>. <what to do>`, never `<what we were doing>: <cause>`. Where the backend named a cause short enough to be a label, that label carries it and the description carries the next step, because the label is read first; a longer one leads the description instead and the generic label stands. This is ordering rather than height: a row that reports a failure keeps the same cut and the same press it has always had, and the panel under it is a column of controls that a failure may not push down the screen.

### QAM home

The normal Decky panel is intentionally narrow and compact. Its stable top-to-bottom order is: the mascot, an update offer when there is one, **Cheat Engine**, **Current game**, **Active Cheat Table**, **Active Cheats**, **Auto-load**, then **Advanced…**. The first two are the only parts of it that are not about the game in front of the user, and both can be absent. The mascot is a durable preference, on by default and switched off under **Advanced -> Panel appearance**, where switching it off removes the image rather than hiding it. It is stored with the other on/off choice in the plugin's own preferences file rather than beside the Cheat Engine registration, so that a build which does not know about it loses neither. The update offer is a single control reading **Update to vX.Y.Z**, drawn in the mascot's own orange. Three things have to hold before it is drawn at all: a newer stable release is actually known, automatic checking is on, and this device can carry the install out. Otherwise the panel has no row, no height and no focus stop for it, which is the panel exactly as it was before updates existed, and Advanced is where a finding the panel withholds is still stated with the reason. **Disable all** and **Advanced…**, plus the stop action while it exists, share one horizontal controller focus group rather than separate vertical steps. **Advanced…** leads that group and takes its free width, because it is the way on from this panel and the half of the row a user walks to, and because that is also what decides where a step down from **Configure cheats** lands: Steam enters a row at the control covering most of the width of the one above it, and reads a row's stated entry preference only when the movement carries no rectangle to match against, which is true of this plugin's own modal footers and not of Steam's panel. Left and right from there are the user's own, and opening the panel itself keeps Steam's normal initial focus, which nothing here overrides. While a launch is waiting to be cancelled that cancel action is the wider control and the step lands on it instead, which is the action that state is for. A line of state that says something short and complete, such as the runtime line while nothing is connected, the pinned-controls note and the reason a table cannot start yet, is read where it is and is not a stop for the controller: elsewhere a read-only row is one, which is what lets a screen made almost entirely of them scroll and lets a clipped one be opened, but on a panel of controls it only rests the ring somewhere with nothing to show or press. The same runtime line keeps its stop while it carries the reason a connected session could not be read, which is the text worth reading and the text that may not fit its line. Validation/session internals do not appear in the normal path.

On first run, Cheat Engine shows **Download and install CE** plus bounded compact progress/cancel state. The action downloads and extracts the reviewed installer locally; it never asks the user to choose Proton for setup and never executes the installer. Runtime launch remains bound to the running game's independently observed Proton and compatibility prefix. A live setup operation is monitored automatically, including after frontend reload; Home never asks the user to press a separate Resume action and never starts a competing operation. After a verified extraction it becomes a card carrying the manifest visible version, whether the registered installation is **Managed** or **Imported**, and its compact SHA, plus a small **Reinstall CE** action behind one explicit confirmation. Reinstall always downloads a fresh copy of the reviewed artifact before extraction; its status says so, and the previous managed installation stays recoverable until atomic promotion and post-promotion validation succeed. Missing/refused/rate-limited/temporary download responses, DNS/TLS/redirect errors, oversized data, wrong installer format, and reviewed size/SHA mismatch display a bounded actionable error and leave the current managed installation unchanged. A consumed successful operation clears local progress before Home repaints readiness and does not wait for an optional read-only launch-capability refresh before re-enabling the normal workflow. When overlapping Decky frontend observers reach the same exact completion, only the observer that performs the durable identity commit emits the one non-empty success notification; the other reconciles through an idempotent exact-operation receipt. Reinstall uses Decky's native controller-aware confirmation dialog; the directional behavior of other paired custom modal actions is settled by on-target evidence and is not inferred from CSS geometry. Manual CE import remains under Advanced as a controller-accessible fallback.

### Current game

While the user is in a game, CE Decky observes Steam's running-session list and maps a running AppID only through the exact installed Steam/non-Steam library identity. Exactly one match is selected automatically. Missing APIs, zero matches, unknown AppIDs, or multiple running games never cause a guess; **Choose game…** opens a dedicated picker, while Advanced retains the same selector only as a diagnostic fallback. That picker lists what this device holds rather than what the account owns, because Steam syncs a library and not its installs: a Steam entry is offered when this device's own manifest says it is fully installed, and a non-Steam entry when this device's own shortcut store holds it and the program it names is on this disk. Two kinds are left out, each on Steam's own record rather than on a reading of the name: an installed app Steam declares nothing to start, or types `Tool` and declares no Windows program, which is every Proton build, every Steam Linux Runtime and the redistributables bundle; and a shortcut Steam made out of an installed application's own `.desktop` entry, which is how a browser, an emoji picker or a streaming client gets into a library beside the games. An app Steam types `Game` is never left out whatever it declares, and a read that fails leaves the whole list rather than hiding a game the user has. The picker's library dropdown sits below its explanation and spans the panel; its opened menu matches that control and remains fitted to the modal window, so long game names do not turn the selector or its menu into a narrow second column. **Use this game** and **Cancel** are compact buttons in one horizontal controller focus group. The same picker stays reachable as **Change game…** once a game is selected, because automatic detection can land on the wrong library entry and correcting it must not require the Advanced screen. A game only has to be *selected* to search, download, import, review and authorize a table for it; it has to be *running* only for Cheat Engine to launch and attach. An explicit manual selection is never replaced by a later automatic observation. Fresh AppDetails must still agree on Steam-vs-shortcut kind before a profile is reused. Changing the game is refused while the selected game is running, because every per-game thing this plugin holds, the selected table, the target process, the consent given for those exact bytes and any owned Cheat Engine, would be left pointing at another game; the greyed control describes that refusal and does not enforce it, so the running state is read again for that exact AppID when **Change game…** is pressed and again when a game is picked, and a state the frontend could not read is recorded and allowed rather than leaving the user no way to change games at all.

The home card shows the Steam card/display name, Steam/non-Steam identity, AppID, and the confirmed target `.exe` basename. Provider search eligibility remains separate from launch eligibility.

### Active Cheat Table

The card is empty until a table is selected. **Search / Download** opens a modal, pre-fills the search query from the current game name, allows controller/OSK editing, searches enabled providers, and, once that attempt settles, shows one bounded paged result list with paging and the way out of the screen on one row under it. Previous, Next and Close belong to one horizontal controller focus group, so the footer never requires changing directional axis; entering it from the results prefers Next. Tables already associated with this game remain in that same result list when providers fail or the device is offline. A provider result is marked Local whenever this device holds a usable table the row can open without the network, whether an advertised content digest resolved to those exact bytes or the table was downloaded from that exact provider row before. A row is marked Imported when its origin is known and there is no usable local table attached to it, so the press has to go and fetch one. Origin identity is enough to offer a saved copy and is not a statement that the row still serves the same bytes: the sources that publish no digest, which is every phpbb attachment source, cannot support one, and a user who has already downloaded a table from such a source and is now offline owns that copy. What the missing proof changes is what the choice says, never whether the choice exists. Pressing a row with a local table opens one compact choice whose sentence names which of four cases it is: the provider's own checksum matches this copy; this is a copy downloaded from this source before and the source publishes no checksum, so CE Decky cannot tell whether the online version has changed; the source does publish one and now advertises a different checksum, so the online version has changed and this copy is the earlier one; or a saved table opened on its own with no provider row in play. The third is not the second: a source that says nothing and a source that says the file has changed are different answers, and reporting the weaker one where the stronger is available tells the user less than is known. **Use saved copy** is focused by default and selects the immutable SHA-addressed bytes without network access; **Download again** explicitly asks the provider for its current bytes, which still pass the ordinary validation and exact-SHA import/review path. The two are gated separately, because they are about different bytes. A durable block against what the row serves, including a file the source no longer has, and a transfer this session already found damaged disable **Download again** and say why, while the saved copy stays selectable. Only a mark about whether that saved copy works, recorded against its own SHA, disables **Use saved copy**, and it leaves the download available. A copy in the library was imported and verified as a table, so a record that some download was not one, that an archive is locked, or that a source no longer serves a file cannot make it absent or unusable: those are about the download side and disable only that half, on either kind of row. One record reaches a row twice, because it is keyed by its exact SHA and again by every provider row it was downloaded from so that the mark is visible on a source advertising no digest, and that second key is recognition rather than a statement about what the row serves now. One provider row also serves several revisions over the years and each can earn its own record, so a row carries every mark it has earned, newest first, and what a record is about is read from its own cause rather than from which revision happens to be saved here. **Failed**, and a record too old to say which of the four it was, are statements about exact bytes: they refuse those bytes and never the download, whether they name the copy saved now or an older revision the row no longer serves. **Gone**, **Not a table** and **Encrypted** are about what came through the row, and what they refuse depends on whether the source has said what it will serve. Where the result advertises a digest, that digest is the answer: bytes already recorded as not working are refused, and a record naming other bytes is about a revision the row no longer offers and refuses nothing, since **Not a table** and **Encrypted** are written against the exact digest of what was downloaded. **Gone** is the one cause with no digest of its own, because nothing was ever downloaded for it, so it stays a fact about the row and needs **Retry**. Where the source advertises nothing, there is no way to tell an old failure from the current file, so the newest of the three refuses **Download again**, gives the row its reason, and **Retry** is what says to try it anyway. A row with nothing usable here and only an exact-byte refusal behind it is named and not offered, since pressing it would spend a transfer to be told by the importer what the badge already says, and **Retry** is how the user says to try it anyway. A row is retired outright only when it has neither half left, and a saved table refused on its own is opened for the same reason: asking the source again is how a table refused for an older build of the game is replaced when that source publishes a fix. A local-only row may attempt **Download again** only when its recorded provider origin is offered by a fresh search; failure leaves the local copy unchanged. **Open Local File** uses Decky's native picker and the same CT/archive validation pipeline.

Global table bytes remain immutable and content-addressed under the managed table store; the per-game library is only a bounded list of exact SHA associations. No user-visible folder name or game title becomes a filesystem trust identity.

Review keeps process lookup compact on every viewport. Its information values stay one clipped line with ellipsis and no extra focus target, so long filenames cannot increase card height.

Every newly imported/downloaded or newly selected exact SHA goes through a review modal. It shows filename, source/provenance, exact SHA, size/record count, executable-content markers, process hints, and the exact target process. Most tables name no process at all, and the library entry commonly points at a launcher rather than the executable that owns the game's memory, so the choice also offers the Windows `.exe` basenames this game's own processes are running right now, marked as running and observed through the same bounded procfs scan that corroborates the prefix. A Proton prefix also runs Wine's own services, Proton's helpers and the game's crash reporter, so the observation is filtered twice. A process running out of the prefix's own Windows directory is dropped when it is observed: a real game is never installed there, so that one directory is identity evidence in a way a store-owned library path is not, and the rule holds for programs a future Proton adds under names this build has never heard of. The remainder is then classified by the same exact-basename list the ambiguous running-game observation already uses for third-party store launchers, extended with the Proton helpers that live in the tool directory rather than the prefix and the crash/telemetry helpers a game ships beside its own binary. Filtering never empties the list. The observation is a display candidate only; it never becomes a launch path or an attach identity by itself, the table's own hints are never filtered because they are the author's intent, and manual entry stays available when the table names nothing and the game is not running. A default is always offered when anything is known, ranked by how exact the evidence is: a process the user already confirmed for this game, then a name the table carries that is also running, then whatever is running that is not the game's own launch executable, then the table's hint when nothing is running. A saved confirmation loses that first priority only when fresh exact evidence identifies it as the launch executable and another game process is running beside it; this repairs an older launcher default without overriding a distinct user-selected process, and an explicit table hint may still name the launcher. That launch executable is observed rather than assumed: Steam records a non-Steam shortcut's target in AppDetails, and a Steam library entry's target appears in the running game's own process table as `<tool>/proton <verb> <executable>`. It is a ranking hint only; nothing is launched or attached from it. A hint that nothing running answers to is not preferred over the observation, because a table published for one store's build names that build's executable. Matching a game's display name against its executables is deliberately not a signal: for the reviewed game it scores the launcher highest while the executable that owns the game's memory shares nothing with the title. Process hints are read from `Address` values and from Auto Assembler scripts, where Cheat Engine writes its own `{ Game : <exe> }` header and where the `aobscanmodule` idiom names the target module; a module that is not an executable is never a process candidate. **Look inside this table** opens what that exact SHA can execute, as text, from the screen that asks whether it may: the table's own Lua script, each record's Auto Assembler script under the name of the cheat it belongs to, a window the table brought with it, and the fact of an embedded file. Without it the consent screen asked its question and offered a count of markers as the only answer, and reading the scripts meant Desktop Mode, a file manager and a text editor, none of which a user in Game Mode has. It reads and never runs. Once the section index arrives, focus moves to its first Read/About row immediately. Reading one section is a single press repeated, so the focus ring opens on Next and stays on whichever paging control the reader is using, and moves to the way out of the window once there is no page after this one. Closing that section returns the ring to the exact Read/About row that opened it, so the user resumes the section list at the same position. The same view is reached from **Advanced -> Active table** beside the file the table is stored as. Sections are listed without their text and fetched one at a time, because one real table holds 529 KiB of scripts across 99 records; each is bounded and normalized exactly as a control label is, so a script cannot render as something other than what it is, and what was cut or normalized is stated rather than silently applied. An embedded file is named and sized and its bytes are never returned, because those bytes are the one thing in a table that exists to be executed elsewhere. Addresses and offsets are not shown here; the cheat list is where those are readable. **Use this table** both saves the profile selection and grants execution consent for that exact SHA; cancel leaves the bytes local but unexecuted. Activation is minutes in the worst case, almost all of it spent waiting for Cheat Engine to open the table and answer, so the screen names the step it is on and how long it has been on it, and offers to stop only while the activation owns a Cheat Engine that stopping would end: the durable profile and consent writes it starts with cannot be taken back, and stopping the Cheat Engine it started ends the activation rather than letting it go on to report a table it no longer has. During a live game, selecting a different exact SHA stops only CE Decky's owned Cheat Engine process, prepares a new session, and starts CE again without ending the game.

Search marks same-content provenance only when distinct known origins resolve to identical final CT bytes. A verified single-table archive mapping may establish this across providers, but a changed archive SHA requires a new resolution. It is a passive neutral glyph rather than a word, drawn in the panel accent so it cannot be read as a second verdict, and nothing infers it from a filename, a URL, a provider row or an archive digest. An exact known cheat failure is compatibility and is the red mark below, which stands whether or not those bytes are also local: **Local** states availability and never hides a failure. Same-content provenance does not prevent selection after the failure is cleared. A damaged payload with no usable CT identity remains **Damaged**.

Search and Manage state compatibility for one exact table as a single passive circled glyph, in one four-state family and in the same language on both screens: green check after a cheat activation and subsequent readback succeed for the exact game/table on a matching known build, amber return arrow when a comparable PE version or Steam build ID changed or the evidence was invalidated, grey question mark when nothing comparable is known, and red cross for actual negative evidence on those exact bytes. Red outranks amber, amber outranks green, and green outranks grey. Red renders whether or not the table ever earned positive evidence, and while it stands nothing renders green; clearing Failed requires a new successful retest to restore green rather than resurrecting the old one. The two halves of the family are scoped differently on purpose, and the wording never claims otherwise: green, amber and grey are evidence for one game and one table, while red is the device-wide record about those exact bytes and stands in every game's search until the user clears it. Both halves of one rendered mark are always about the same exact table: a row presenting a stored copy marks that copy, a row with none marks the revision its source says it would serve, and a record about other bytes, such as a refused newer revision beside a saved copy that works, never reaches that mark. The visible surface is the glyph; the sentence, including the recorded failure reason, is its accessible name, so a row gains no words, no height and no controller focus stop. **Gone**, **Encrypted**, **Not a table** and **Damaged** are conditions of the source or of the bytes rather than compatibility states: they keep their own cause-specific presentation, never colour this glyph, and never take away what a cheat has already proven, because a table that did load and did work is not answered by a statement about a download. No mark grants execution consent or changes offline availability. **Local** is physical presence and nothing else: a failure removes neither the bytes nor the word, and the row goes on offering them, while newly taking those bytes up stays refused until the user clears the record, which is the one press that changes it and needs no network. That refusal is one rule in the backend rather than one screen's manners: a new association, a new selection and a new authorization of an exact table recorded as not working are refused wherever they are asked from, so **Use saved copy** in Search and **Use** in Manage agree. A table that was already selected or already authorized when the record was written keeps both and its running session is untouched, because withdrawing those is what Revoke offers and the user's decision to make. Source and payload conditions refuse nothing here: they are about bytes that never became a table or about a provider row. They also say nothing on the surfaces that are about a stored table: Home never calls the table a game is using not working for one, Manage does not read its sentence onto a library row that has no source context for it, and neither one invalidates proven history. They stay where they mean something, which is the provider row the download came from and the full list under Advanced. The backend keeps the same line: only a record that a table did not work dates the positive evidence about it or stands between it and a fresh proof, while a payload or source cause refuses the exact bytes at import, which is what it is for.

Stopping the Cheat Engine this plugin owns switches the table's own cheats off first. A cheat is applied by rewriting the game's code, and the script's `[DISABLE]` is what puts it back; a stop kills the owned process group, so that half never ran, and the patches and the allocation stayed in a game that kept running. Nothing later could undo them either, because that restore resolves symbols belonging to a Cheat Engine that no longer exists, and only restarting the game cleared it. The running bridge is asked to put its records down, innermost first and enclosing Auto Assembler scripts last, since a record's bytes live inside the allocation its script made. A cheat that is simply on or off is left at its off value rather than only released: releasing the freeze leaves in the game whatever value the record was frozen at, so a table of on/off flags would otherwise come down with every flag still on, and the key each one is off at travels with the session from the same inspection the user reviewed. One exception, and it is the same rule Apply and Auto-load already follow: a flag its own script allocates whose hooks could not be proven to survive being written off is released and not written, because that write is what kills the game minutes later. The walk is what puts such a flag back, since its script comes down in the same walk and the table's `[DISABLE]` takes the patch and the allocation the flag gated with it. A switch the game itself owns has no script behind it and is always written, or it stays on in a game that goes on running. Which of the two a record is comes from its address, never from where the table files it: a plain `game.exe+10` switch grouped under a script is still the game's, a script's flag filed in a group of its own is still the script's, and a symbol counts whatever its case, quoted or with a constant beside it. What a bracket or a pointer's offsets reach is the game's. While this runs nothing may switch a cheat back on, because the stop ends Cheat Engine as soon as it answers and a record switched on behind the walk keeps its patch; an activation Cheat Engine has not finished is waited for, and what is switched on then is asked for again rather than assumed. The answer is where that session stops touching the game: a startup rolling itself back can switch a record on again, so once the answer is out nothing here runs, and work that had not finished is named in the answer instead. What a failed startup could not put back is named too, whatever the walk itself found: those records are not switched on, so no walk will ever reach them, and they are still holding what startup wrote. The walk's own list is what it managed to ask about rather than what the table holds, so a record Cheat Engine would not answer for, and a mutation whose state could not be read, leave the stop unconfirmed rather than counting as off. It is published inside the bound the stop waits under rather than one of its own, because an answer that arrives after Cheat Engine has been killed is an answer nobody reads. Where none arrives, the screen says so and names restarting the game as what clears anything left changed: an unread answer is not a clean stop. Nor is an answer that established nothing. What lets the stop stay quiet is a walk that finished with nothing left switched on, or the game's own processes proving it has exited and taken every patch with it - proving, because a scan that ran out of budget and a process this device may not read are not a game that is gone; and proving it of every program this session was pointed at, because a retried attach moves the session to another program and leaves what it had already changed in the one it moved away from, so the program the profile names can be gone while the game carrying those changes is still running; an address list that could not be read, a bridge that went quiet while the game is still running and a stop nothing could be asked of are all the same news to the user. A mutation Cheat Engine had not finished when the command that asked for it gave up waiting is remembered until Cheat Engine is done with it, because a command's bound is this plugin's decision and not the operation's end: the walk cannot answer over one, and a record still moving at the deadline is named. The walk also looks once more after its last pass, whatever it has spent: a table whose own `[DISABLE]` switches the next record on is an ordinary shape, and an allowance that ran out is not a game that is clean. It is bounded twice, per record and over the whole walk, and the stop proceeds whatever the answer is: a stop that became less reliable than the one before it would be worse than the leak it closes. The screen says the cheats are being switched off, because that runs more of the table's own code than anything else CE Decky does, and where a cheat could not be switched off it says which and that restarting the game is what clears it. A stop that ended a Cheat Engine without proving every cheat put down or the game gone holds that game: until that run of it is proven over, choosing a table, starting the one it has and **Auto-load** all go no further, nothing is saved or started, and the reader is told to restart the game first. A table started there would meet patches it did not write, which nothing can put back: its scans would miss, its startup would fail, and the failure would be recorded against a table that works. The stop itself still only warns, because ending Cheat Engine is its whole job, and it is the next start that is held, whichever path makes it. The backend owns the hold and keeps it on disk, one per game, so it outlives the panel, a reload of the plugin and a second game held beside it, and it refuses the start itself as well as the panel doing so. It is lifted only on proof: every process of the run it was taken on gone, those being its PIDs with their start times, which the next run of the same game cannot share; or, where those could not all be listed at the stop, every program the session was pointed at proven absent by a complete walk. A process table that could not be read, a walk that ran out of budget and a process it could not read that may be the game all keep it. Home says the game is held before anything is pressed and offers **Clear**, telling the reader what clearing it without a restart costs, because a device whose process table never answers would otherwise hold that game for ever. Every start is admitted against it under the same lock that says a stop has begun, and the stop marks its game before it ends anything and unmarks it only once its verdict is held, so no start is admitted in the moment between the old Cheat Engine ending and the hold that says what it left; a stop by operation, which asks nothing of the bridge, holds its game the same way. What a stop holds the game on is read from the session it is stopping, as it begins and before it ends anything: every program that session was pointed at, a retried attach included. Read again once Cheat Engine is gone, a revoked table, a new target or a retired session would leave only the profile's own program, which can be gone while the one a retried attach patched still runs. So while a stop runs nothing may change that game's profile, table or session, and those requests are refused until it has finished. The holds this process knows are the ones in force: a write to the file that fails leaves them in force and says a reload would forget them, and a hold that could not be taken with its evidence is taken without it. A file that cannot be read is not read as holding nothing, because it may hold a game still running what was left in it: every start in every game is refused, nothing overwrites it, and Home offers **Clear**, which starts the record over and says what that costs. There is no switch to skip it: the bound is what makes running it unconditionally safe, and a setting whose only correct value is the default is not a setting.

A table's scripts find the game's code by scanning for byte patterns, and one pattern being absent from the build in front of the user stops the whole script compiling: every cheat that script owns goes dead at the same moment, the table still loads, and nothing anywhere says why. Review reads the patterns out of the table and looks for them in the game's own program before consent is asked, naming how many the table looks for and which of them are not there. It runs only where the program is already known - the running game's own executable, or the path this device's compatibility record kept from the last time a cheat for that game worked - and where neither answers, nothing is checked and nothing is said, because guessing a path is what this project is most careful not to do. More answers than two: a pattern looked for in another of the game's files, one looked for between two addresses that only exist once the game is running, one with no literal first byte to search for, and one a spent budget never reached are all reported as not checked rather than as missing, and none of them puts a sentence on screen. A pattern that names one of the game's own files is looked for in that file where this device can find it beside the program - a bounded few of them, under the one budget the whole check has - because answering only the program reads half the table and shows the reader the healthy half; a file this device cannot find stays as unchecked as it was. And where a pattern is found in more than one place, that is said: Cheat Engine's own documentation of its scanner is that it returns any one of the matches, so a pattern that is not unique in this build is a hook that may land in unrelated code. It is reported as a second place actually seen and never as a claim that the others are unique, because proving uniqueness costs a read of the whole program for every pattern - six times the cost, measured - and a screen may not spend a reader's Review proving what it can only report. A program a protector or a DRM wrapper has packed is refused whole, since its code exists only once it is running and every pattern would otherwise read as absent. The block Review says this in carries at most two findings, the most consequential first, so a screen that asks one question never opens with four answers. What a copy may have taken out of it is narrower than what is reported: only a pattern whose script names the file it is looked for in, because a script that searches the whole running game, or a range of it, is looking in more than any one file holds and a pattern missing from that file is not a pattern the game does not have. Such a pattern is named to the reader and left in the table, since cutting a hook out on it could make the copy less of a table than the one it came from, and Review says the two apart: a pattern proved absent from the whole of where its script looks is a cheat that will not work, and one merely not found in the program is said as that, with where else it could be. The file that counts as that whole is the program this device knows the game runs, and only that: `aobscanmodule` searches the module the running process loaded, and a file of the right name in the game's directory is very probably that module and is not established to be it - there can be two of them, the search for them is bounded in depth and in entries, and the module may be loaded from outside the directory searched at all. Such a file is still searched and what it does not hold is still said, because not finding a pattern is worth saying; what does not follow from it is taking the code that needs it out of a table. And a symbol the table uses twice for different code is left out of the answer rather than answered for by whichever script comes first in the file. A symbol the table declares more than once is refused for the same reason, because one script per graphics backend is an ordinary shape and which of them is the one that is missing cannot be told apart by name. Where the pattern is missing there and a copy without the code that needed it is one CE Decky can prove, the same **Prepare a copy that works here** press offers it, and the copy's own Review names the scans that went and the cheats that went with them before the consent for it is given; the press is offered for a repair that was made and proven rather than for the fact that something is missing. The panel names a copy CE Decky made `Fixed` where it names a downloaded table by its source: `Local` says only where the file is, which is true of every table the panel can show, and what the reader needs about this one is that it is not the table they downloaded. Advanced's **Active table** carries the row such a copy otherwise has nothing in: the row that names where a table came from is absent for a derived one, because no provider served those bytes, so its place is taken by one naming the table it was made from - by filename where this device still holds it, by digest where it does not - what was taken out of it and whether any cheat went with it. That row is one line, and the whole account of the change is behind the press every row there carries. A table can be both signed and missing a pattern, and then one press removes both in one step and stores one copy carrying both transforms: a user meeting them one at a time would make two copies, consent three times and be left with two near-identical tables to tell apart. Review can only ask the scan question where this device knows which program the game runs, so a table that got past it unchecked meets the same offer from the other end: the dialog that opens when a cheat is switched on and comes straight back off gains **Try a repaired copy** ahead of **Stop using it**, and falls back to the two answers it always had where no repair can be proved, saying that it cannot rather than offering a press that would refuse itself.

Some tables carry a `<Signature>` element, and this Cheat Engine refuses every one of them: it returns false from its own load, raises no dialog and writes nothing to its log, so a user who starts a game to try such a table learns only that nothing happened. CE Decky reads the element structurally when it imports a table and records the answer beside the table's other facts, because the screens that list tables never parse one; a record written before that was read carries no answer at all and is filled in from the bytes at the next startup, since a row must never call a signed table unsigned. Review states the fact in the same **What CE Decky found** block as everything else it read in the table itself, and states what it costs the reader rather than what this project measured. It refuses nothing: the table is still importable and still consentable. Beside the sentence is one press, **Prepare a copy that works here**, which stores the same table with the signature removed as a table of its own and opens Review on it; the consent is given there, for the bytes that will actually be loaded, and that screen says what changed, which table the copy was made from and that no source vouched for these bytes. The same press is on the Manage row, where a table already on the device is chosen, because that is the other place a user meets one. Rows gain marks rather than lines: an amber **Signed** chip beside the compatibility glyph, which is deliberately a different shape from that glyph because a signature is a property of the bytes known before anything is tried while the glyph is a verdict earned by running the table, and a mark on a derived row. A derived table sits in the library as an ordinary flat row rather than grouped under its origin, and the one line it adds names the table it came from, in the slot the row already spends on where its bytes came from.

### Active Cheats

The home shows only active states confirmed by the current exact resident bridge; it never treats staged UI intent as live state. The summary is bounded (first eight plus a remainder count). **Configure cheats** opens a separate modal with All/Pinned/group sections, bounded paging and optional filtering so large nested tables remain controller reachable. Its paging and Apply/Cancel actions share one compact footer, with page navigation first and the commit/exit pair together at the right edge. All four buttons belong to one horizontal controller focus group, so reaching an action never requires changing directional axis inside the footer; entering it from the cheat list prefers Next. Pinning is a per-exact-SHA profile write committed on its own, never part of the Apply diff, so the Pinned section stays populated by explicit user choice rather than by runtime state.

Opening the modal queries every safe actionable record in the exact current session, and the home derives **Active Cheats** from that complete exact-session snapshot rather than the runtime status file's bounded recent-result window. The user stages Active/value/dropdown changes locally. **Apply** computes a diff only for fields the user actually touched, preserves static table parent-before-child path ordering, writes values before activation where both change on one record, waits for exact generation/MemoryRecord ACKs, then re-queries the complete safe-control set and succeeds only when the requested final state is confirmed. A pending/unknown ACK is not retried blindly. Group headers, duplicate/unsupported IDs, and invalid read-only dropdown values remain non-actionable. A record that chooses from a list is offered at most 24 values at once whatever the table declares, and past that threshold the list is narrowed by typing first: a controller walks a Decky dropdown one item at a time with no search and no way to jump, and a real table declares 6508 items in one picker. So the size of the list a table carries is a parsing question rather than a rendering one - Steam is never handed a large dropdown - while the record's own value is always among what is offered, taking one of those places rather than an extra one. The section picker names each section by what it adds rather than by its whole path: the groups every section shares are dropped, and so is any group that is an option of its own above it, which a CT always places immediately above its descendants. Whitespace inside a name is collapsed, because these are headings an author wrote rather than labels. Whole groups are then dropped off the front while the name does not fit the width of the list, in silence: what goes is either the option this one sits under, which is on the screen, or a heading the picker never offers, so a mark saying it went would point at nothing. Only a section's own name being longer than the line is cut, at its end, so that a name can never wrap and push the rest of the list down. Two options that would read the same are given back one group of their own path each until they differ.

A record whose list is exactly two entries that say off and on is drawn as a plain switch: no list, no field, and the row's own toggle is the whole control. A record that keeps its list draws the list alone, with the free field one press away behind **Type a value instead**, because no table in the sampled corpus declares its list exhaustive and the field has to stay reachable without being a second control on every row; a record already holding a value its list does not offer keeps the field open, so the reader's own answer is never behind a press. A list declaring a single value draws the field and no list, since a list of one is a control with nothing to choose from; where the author declared that list read-only, the entry stays, because it is then the only value the record may take and there is no field to offer in its place. Which two entries those are is the author's own labels, read in the backend against a small fixed vocabulary, and the key written for on is whatever that author gave the positive side rather than `1`, because a real table's pair is sometimes `2`/`1` or `1040`/`2400`, and in three tables of the sampled corpus the active side is `0`. Switching such a record off writes the other key after releasing it: releasing the freeze alone leaves the record at the value it was frozen at, which is a cheat still running in the game under a switch that says it is off, and **Disable all** puts every switch back to its off key for the same reason. A two-entry list the vocabulary does not place keeps its list, because those pairs are two named alternatives, `Male / Female` or `Set Own Ammo / Unlimited Ammo`, where the labels are the information; the pair is recorded in the plugin log so the next version's vocabulary is chosen from what users met.

A table's own Auto Assembler script allocates the flags it declares and gives them its author's defaults, which are not modest: one real table declares 22 of its 24 flags as on, so enabling that script for one cheat switched on damage multipliers, movement speed and the rest while the panel counted the one cheat. Every switch a script declares as on and the user did not ask for is written to its off value in the same call that starts that script - whether CE Decky started it to reach a cheat under it or the user switched it on themselves, since the defaults arrive either way - and the same holds for **Auto-load**, so the next session does not put them back. Only a script this press starts: one already running had its defaults dealt with when it started, and writing them again would undo a flag switched on since, while one that is not running has not allocated those addresses at all and the writes would be to nothing. Only records the enabling script itself allocates are touched, which is what makes them addressable the moment it has run; a declaration that cannot be read holds nothing off rather than guessing. And only a flag whose own hooks were read and found to survive being written off: a table's hook can turn a pointer into an offset, test the flag, and on the branch taken when the flag is off hand the game back the offset, which kills the game minutes later with nothing to say a cheat table was involved. That reading answers in one direction only, so a flag it could not follow is treated exactly like one it found unsafe: the cheat stays on, the row in the picker says it is not safe to switch off, and the press that started the script says which cheats are on that nobody asked for. So does every startup that is said to have succeeded, whether **Auto-load**, the start button or a table just chosen: the backend answers from the same plan the session was prepared from, because a startup's own success message is about the cheats the user chose and these run beside them. What ends those is the script coming down when nothing under it is on any more, which takes the allocation their flags live in with it; writing them off is the one thing that is never done on the user's behalf. What the panel counts is then what is running. Review says this once, in the one **What CE Decky found** block that screen has for what CE Decky read in the table itself: how many of its on/off cheats the table switches on by itself, counted over the records the picker will actually draw. It promises that CE Decky turns on only the ones the reader chooses where every one of those defaults can be held off, and otherwise says how many stay on whenever another cheat of the same script is on. The block is absent when there is nothing to say, which is the test for every addition to that screen.

A script may create or destroy descendant MemoryRecords dynamically. The bridge therefore gives an absent record a typed `record_missing` result, which the frontend may treat as expected only when table topology and the requested transition explain that absence. Target detachment, AddressList failure, record-read failure and mutation failure remain operation errors; they never become “waiting for its script,” a successful **Disable all**, or a durable remembered-off selection.

The last confirmed user selection is persisted per game and exact table SHA only after Apply verification. Fields the user did not touch retain their previous remembered value instead of silently absorbing unrelated live CE drift. Previously persisted/touched inactive states are retained when needed so a former active cheat is not silently re-enabled by older startup state. Live control has its own product limit, separate from the static parser ceiling: a table may be inspected, imported and reviewed at the parser's full size, but one live query or bulk mutation addresses a bounded number of controls, because each batch is a status read, a durable write and acknowledgement polling. A table beyond that limit stays usable for inspection and Auto-load while live picker/snapshot/bulk operations report the limit instead of issuing thousands of round-trips. The snapshot is an optional post-launch capability, never part of a launch's success, for every table size: table activation, manual start, exact-PID retry attach and Auto-load all complete normally whether the snapshot is skipped because the table is beyond the limit or the read-only query itself fails. Home then says live controls are unavailable and why - the table's size, or the exact read failure - rather than pointing at a picker that would refuse it or reporting an attached, started session as a failed launch. Startup progress is published by the bridge as its own monotonic count, because the result list it also publishes is deliberately bounded and cannot be used to tell whether a long startup plan is still advancing. A multi-batch query also stops issuing new generations as soon as the screen that owns it is closed, so an invisible query cannot compete with the next controller action for the same control log.

Persistence is bounded before the first runtime mutation against the backend's exact expanded plan for the table - the stored configured values and the enclosing scripts the selection implies included - so a selection can never be accepted, applied to the running game, and then refused persistence.

A durable profile write is exact desired state, so a lost reply is reconciled rather than reported as a failure: the backend saves atomically and `get_status()` can be asked what is actually stored, and only a rejection the backend itself raised proves the write did not happen. When neither the write nor the authority can be established, the outcome is reported as unknown and ordinary "nothing was saved" semantics are withheld. That inference holds per mutation, not per action: a rejection proves only that the write it came from did not happen, so an action that commits several independent settings reconciles each one on its own and carries what already committed into the failure of the next. Catching a panel up after a commit is never part of the commit either, because state that is already stored must not be reported as unsaved by a failed status read. Acquisition completion follows the same rule against its exact acquisition ID. A failed Apply names every surface it already reached - the running game, this table's saved configuration, or an unknown durable outcome - because one Apply can reach more than one, and closing the picker acknowledges them rather than passing over them silently.

The source switches are durable writes on the same terms, reconciled against the record of switched-off sources rather than against a profile. The reconciliation asks whether that record now holds the exact position the switch was for, which means asking about the one source being switched, not requiring every source in the roster to be in it: testing one provider's desired position against all of them is false for every other provider, so the path that exists to recognise a committed write reported all of them as uncommitted.

A value the user types or picks is that table's own configuration, kept separately from the reconciled live state. Apply commits it for the exact SHA before any runtime mutation, so an address Cheat Engine cannot read yet, a rejected write, or a failed activation cannot replace the choice with whatever the game happened to hold. The picker shows the live answer wherever the session has a readable one and the configured value where it does not; emptying the field drops the stored value rather than writing a blank. A record this press switches on and that takes a value must carry one, and so must one that is pinned, refused by name before anything is committed or written. Neither switch is ever disabled for want of a value. A staged control that cannot be pressed is a screen refusing to be used and leaving the reader to work out why, so Active and Pinned always move and Apply is the one place a missing value is reported, for both alike. Pinning is included because a pinned cheat is a switch on the quick access panel with nowhere to enter a value, so one pinned empty could only ever be switched on empty, and the press that would do it happens on another screen and later; pinning itself stays committed on its own and is never refused. A refusal is said once, beside the control that earned it, under a heading naming that control, and it is dropped as soon as the reader does anything else, because it describes one press against the state at that moment. The rest of that rule: Cheat Engine freezes whatever the game happens to hold at that address, so switching one on empty is not a cheat that does nothing, and it was being accepted, saved into the table's startup state and reported as applied. The refusal covers exactly the records this press switches on. A record already on with no value is a state the picker did not create, and emptying the field of one that is already on stays the supported request it was. Auto-load applies the configured value over the remembered one for the same MemoryRecord, except for a record the user explicitly switched off: its value is retained for whenever the cheat is switched back on and is not written at startup. Switching every cheat off does not manufacture explicit-off intent for records that were never on, and the startup plan never asks for a record whose enclosing script this same startup leaves off.

### Auto-load

**Load last table & cheats** is a per-game policy, armed either from the Home toggle or by configuring cheats for the game while Cheat Engine is not running.

That second route is deliberate. With nothing running, a selection made in Configure cheats has no way to reach Cheat Engine except through Auto-load, so switching a cheat on there *is* the request to apply it; requiring the user to then find a separate toggle would make Apply appear to do nothing. Apply therefore arms the policy in the same durable transaction, but only while the selection actually leaves something for Auto-load to do - a cheat switched on, or a value on a record whose active state the user left alone. Switching every cheat off disarms it again by the same rule.

Auto-load starts the table whenever the game runs without it, and a Stop leaves exactly that state, so a Stop the user makes, from Home or from Review, keeps Auto-load from starting it again for the rest of that run of the game. The switch keeps its setting and the stop's own message says so. The backend keeps that hold beside the one above and lifts it the same way, on proof that the run is over, and also when the user starts a table themselves or switches Auto-load on. A stop CE Decky makes on its way to something else, such as a table switch or a new target, holds nothing: that operation starts Cheat Engine itself or relies on Auto-load to.

Because arming is a durable decision about automatically executing an authorized table on a later game launch, the picker must state that consequence **before** Apply, not only in the result afterwards. Exact-SHA execution consent is a separate and stricter boundary that this never relaxes: Auto-load decides when an already authorized table runs, never what is authorized. Arming is enabled only when the profile has an available selected table, exact-SHA execution consent, and a confirmed target process. Disarming is always available while the profile's exact table identity is readable, because withdrawing automatic execution reduces authority: a missing table blob, a revoked consent or an unconfirmed target must never leave an armed profile the user cannot switch off. Auto-load itself does not depend on the optional managed-install capability; the registered Cheat Engine's own validity is what gates it. On a later launch CE Decky may prepare/start only that same authorized SHA and applies the remembered confirmed state as the startup profile. A different downloaded table SHA is never trusted, consented, or MemoryRecord-remapped automatically.

Provider provenance keeps artifact identity and table identity apart: the digest a provider advertises is the identity of the bytes it served, so it stands for one imported table only when that artifact could yield no other - a direct `.CT`, or an archive with a single member. A multi-member archive records which member was taken and how many there were, and its result keeps reopening member selection rather than resolving to whichever table was imported first. An origin that declares no member count at all proves nothing about cardinality, so only a direct `.CT` origin stays unambiguous without one; an archive origin without a declared count is reacquired and re-inspected rather than standing for the member already imported.

A provider that answers an anonymous request with a challenge is reported as unavailable in the results and skipped; stable v1 offers no browser handoff for it, because browser use is not a controller workflow and Local file is the fallback that is. An encrypted member of an archive only 7-Zip reads, `.7z` or `.rar`, is deliberately not supported, because the external tool would receive the password on its process argv; such a member is reported as unsupported, and every surface that can select one hides the password field, refuses the import and states why, rather than presenting a disabled action with no explanation. An archive whose members are all unsupported is terminal at inspection, because there is no selection that could lead anywhere; a mixed archive keeps its supported members selectable. Encrypted ZIP is unaffected. An archive password the provider published in the public text beside its artifact stays backend-owned: the first import attempt is made without a password so the backend can try that exact hint, and the controller prompt appears only once that attempt fails. The hint is never displayed, logged, or persisted.

Legacy exact-SHA startup preferences remain readable for backward compatibility and still execute whenever that exact table prepares a session, so Advanced states how many remain and can clear them for the exact table. When autoload is enabled, remembered confirmed state overlays the same MemoryRecord IDs for that exact SHA; no cross-SHA remapping exists in stable v1.

### Advanced / diagnostics

Advanced opens with the two sections that are about CE Decky itself rather than about a game: **Plugin updates**, which carries the update state in the user's terms, **Check now**, the switch for automatic checking, the same update press as the panel and withheld on the same ground, and, after a failed install, the exact path of the verified archive with what to do with it; and **Panel appearance**, which carries the mascot switch. A check that could not finish is never reported as being up to date. Advanced also contains the table-source switches with their per-source statistics, manual game selection, manual CE import plus de-registration of the currently registered Cheat Engine, CE no-game self-test, exact target-process override, support-bundle collection, table inspection/authorization revocation, legacy startup-action visibility and removal, plugin removal readiness, runtime/session status, guarded repair of unreadable session pointers and malformed durable CE ownership, refresh actions, and target/developer diagnostics. Malformed ownership is quarantined only after a complete launcher-scope scan proves that no process carrying any CE Decky descriptor can still exist; ambiguity leaves it blocked. The plugin self-test reports three states rather than two, because its verdict is about blockers alone while several of its checks are deliberately not blocking: whether the panel's durable record can be written and is still private, whether this plugin's own system journal can be read, whether the managed root has room left, and whether the registered Cheat Engine is still the one that was registered. A result with no failures passes, one whose only failures are non-blocking is a warning, and a blocking failure fails; a warning and a failure both name every check that failed and the reason it gave, on screen and in the message that announces the result, because a diagnostic that detects the condition it exists for and then reports success is worse than not running it. Its longer lists open as screens of their own in place of the panel rather than as modals over it, and leaving one returns the controller ring to the exact row whose press opened it, so a reader resumes a long screen where they left it rather than at the top of it. These controls remain controller usable but are not prerequisites for the ordinary flow. Everything a controller-only user could otherwise only repair from a terminal stays reachable here; read-only developer dumps that a Game Mode user cannot act on do not.

A table recorded as not working is recognised in search by its exact content digest and by the provider rows it was downloaded from, the second of which is recognition of the post and never a statement that the post's current bytes are those bytes, and its row says which of the four things happened to it: the red compatibility mark above for a table that ran and did not work, and **Not a table**, **Encrypted** or **Gone** as their own chips, because those are conditions of the bytes or of the source rather than of the table's fit for the game. Under **Advanced -> Tables that did not work** the same entry is headed by its game and then its table, in that order, because that list spans every game and is scanned by the game. That mark shares the row title's own line, against the right edge, so a marked row is exactly as tall as an unmarked one and nothing about the mark can widen the panel: the title is the half that gives way to an ellipsis. The digest is the stronger identity but a result advertises one only sometimes, so on a provider that advertises none the mark was invisible on exactly the rows it had been recorded from. A press that clears marks clears the exact tables it is beside and no others: the list's own Retry clears what the visible rows are showing, and a refusal the row cannot show, which is a newer revision the source is offering beside a saved copy that works, is cleared from the window that names the two apart. A record about bytes a row is no longer offering stays in the device-wide list rather than being dropped by a press that never named it. A record's own summary says what the list holds rather than reducing it to one cause: a table that ran and did not work is keyed by its exact bytes, an unusable or encrypted download by the bytes that came through, and a file a source no longer has by the provider row, because nothing was ever downloaded for it. What a record refuses is stated where the user meets it: these exact bytes are marked, the copy stays on this device and search goes on showing it, nothing may be newly set to use those bytes until the mark is cleared, and a provider may still serve a different revision. Clearing one removes that refusal and nothing else, so a success it invalidated stays invalidated until a cheat proves the table again. Marks are never cleared implicitly: a fresh search keeps them, because this screen searches by itself when it is opened and clearing there made the mark last until the next glance at it. Clearing is an explicit press that appears only while the visible results contain marked rows, names how many, and clears those exact tables rather than the whole record, which remains what Advanced clears. A marked row is one actually presenting a mark, decided by exactly what decides its badge and its two presses: a row whose source has replaced its file and advertised a checksum for it has outlived its old records, and a row holding a usable saved copy says Local rather than naming a revision it is not offering. Neither contributes a count, so the press is never offered over records the screen is not showing. A row clears both of the things one failed download can leave, the durable record and this session's own memory of it, because clearing one and leaving the other put the same row straight back with a second press beside it, and it clears them only where that row is the one making that statement. It clears nothing else: a row can have earned a record per revision over the years, those are statements about different tables, and the ones it is not showing stay in the device-wide list until something names them.

Reporting a problem is a single press. **Report a problem -> Collect** writes one archive of logs, configuration, state and the active cheat tables under the Steam user's home and then reports its exact path in a dialog with one button, because a Game Mode user has to find that file afterwards from a desktop session or a file transfer and a notification that scrolls away with the path in it is the same as no path. What could not be collected is listed with its reason rather than silently omitted, since an unreadable state file is usually the fault being reported. The panel's help text and the archive's own `README.txt` state what it contains before it is attached anywhere. This is the documented bug-reporting route, and the project README describes it as such.

Reviewing a table names the exact Windows executable Cheat Engine will attach to, and it can be named before the game has ever been started. The evidence is ranked and each candidate says which kind it is: a process this game is running now, the executable Steam asked Proton to launch, a name the table itself carries, and last what is known about a game that has never run. That last one is what makes the screen usable at all for the ordinary case, which is a table that names no process for a Steam game that is not running: a Steam library entry's launch executable exists only in the running game's process table, so **Use this table** could not be pressed until the game had been launched once. Steam's own record is what answers it. The client cannot start a game without knowing what to start, so CE Decky reads the same launch entries the client uses, for the branch this device has installed, and offers the program they name, marked **Steam starts this**, preselected, with the screen saying that nothing has been seen running yet and that a game which starts through a launcher of its own declares the launcher. Where that record says nothing, or names a program this device does not hold, the Windows executables in the game's own installed folder are offered instead, marked **in this game's files**, and only a folder whose root holds exactly one of them preselects anything: two at the root is a question the reader answers. Half-Life 2 is why the order is this way round. Its folder holds twenty-eight Windows executables, twenty-seven of them SDK compilers under `bin/`, and Steam's record for it holds one line, `hl2.exe`. The check is real: when the game is running and the process saved for it is not among the Windows programs it started, the panel says so before Cheat Engine is started and Advanced names what the game did start, offering it as a one-press repair only where there is exactly one candidate. With several it names them and leaves the choice to the target field, because writing one stops the Cheat Engine running now and this cannot rank them. Nothing is said at all while that absence cannot be proved, and the bar is deliberately high: a game that is not running, an observation holding no Windows process, a collected list that reached the backend's own cap and may therefore have been cut, or a list with nothing left in it once Wine's and Proton's own machinery is dropped. That last one matters most, because it is what a prefix still starting looks like and equally what a game that has already exited looks like, since the launch observation keeps reporting the AppID while wineserver, the Proton chain and Steam's reaper outlive the game.

Processes lists what Cheat Engine can be attached to, and is available whenever a game is selected. With a live exact session it asks that Cheat Engine, which is the only thing that can supply a Windows PID, and an exact PID may then be attached to. Without one it reads the game's own Windows executables from the host process table and offers them as a durable target-process choice for the next start. Restricting the control to a healthy session disabled it in precisely the situation it exists for: an attach that chose the wrong program is the common reason no healthy session can be produced.

A list a reader scans rather than reads is one fixed-height row per item, and it is the same shape wherever one appears: each of its two lines is clamped to one line and reveals itself by scrolling while the controller ring is on the row, so a row carrying a long name is the same height as a row carrying a short one and a page of them is a known number of pixels. That covers Manage, the search results, the cheats in **Configure cheats** and the not-working records. What leads such a line is what the list is scanned by: a short statement of the row's own state where it has one, then the release, then the date, then everything else, with the whole of anything shortened reachable from the row. Marks and chips sit outside the moving line and never shrink, so a glyph is readable the moment the row is. A row opened by **More** is the exception and wraps instead, because that press is the reader asking for the whole of it. How many rows a page holds is measured rather than assumed: the page each list is built for is what a 1280x800 modal fits, and where the screen is shorter the list reads the room it actually has from its own top and the footer under it, because the chrome above these lists is Steam's own controls and a banner that is there only sometimes. Both numbers are logged, so a page that comes out wrong on a screen nobody here has is answerable from a support bundle. **Sessions by app** under Debug is last on its screen and paged, because it is the only list there that grows on its own, one row per game this device has ever prepared a session for; each row names the game where the library or a not-working record still can, and keeps the AppID either way.

Every section on every screen is headed by CE Decky's own heading, rendered as the section's first child, because Steam's section title puts its text in a shrink-to-fit element whose class is a bare content hash on the shipped client and the rule that separates one section from the next cannot be attached to it; repository QA refuses the Steam title so the two cannot drift apart again. What that heading is made of, and the accent beside a summary row, are custom properties declared once on the panel wrapper rather than literals spread through the rules. A list whose first row is its own summary is headed by that row rather than by the caption alone: the totals are a row of data, so they are set a step darker than the panel and hold the rows that follow off themselves, while the caption above stays text and a rule. A row that carries no control the controller can reach, which includes a row whose only action is disabled, is a focus target of its own: Steam scrolls a panel by moving focus into it, so a run of read-only rows at the end of a screen cannot otherwise be scrolled to at all. Such a row is always given an activation, because a focusable container holding a control is a target on account of that control while one holding only text was observed on the target to be reached only when it could itself be activated. Pressing it wraps its truncated text rather than doing nothing.

Decky workflow modals are detached React trees. They must not assume parent Home props will live-update after `showModal()`: long-lived modals keep an explicit reconciled local view, and any game/library/runtime refresh returns the exact snapshot used to update that view. Search/archive → Review transitions close the old modal before opening the next one to preserve controller focus ownership. Passive/search work remains cancellable, but once a table/runtime/import/setup/Advanced action crosses into its state-changing commit, a synchronous modal-local latch ignores Back/Close until that commit settles; a dismissed detached modal must never complete a hidden mutation. Runtime actions in Home or Advanced are enabled only when prepared and bridge status agree on AppID, table SHA, session ID, CE SHA and descriptor SHA; `connected=true` alone is never sufficient.

## 6. Managed storage

Use Decky's environment as the path authority:

```text
DECKY_PLUGIN_SETTINGS_DIR/
  config.json

DECKY_PLUGIN_LOG_DIR/
  <Decky-managed current log>

DECKY_USER_HOME/.cheat-engine-decky/
  ce/          reviewed installer cache, managed installations, and private runtime copies
  tables/      immutable SHA-addressed table storage
  state/       profiles, sessions, descriptors, controls, and status
  cache/       bounded provider indexes, search cache, and diagnostics state
  tmp/         same-filesystem staging
```

Settings and logs use Decky's dedicated directories. Proton-visible CE, table, and session artifacts stay under `DECKY_USER_HOME` because Valve shares the user's home and Wine exposes it through `Z:` on the intended path. Do not use `/home/deck`, `Path.home()`, or a root flag as the authority.

Every poll rate this plugin runs is paid for in something a user can feel, and they are not the same something. The bridge's control poll buys how quickly a toggle takes effect under the user's thumb, so slowing it is a latency trade and is refused as one. The session's own liveness checks buy how quickly an owned Cheat Engine notices the game has exited, which nobody is waiting on. That asymmetry means the cheapest thing to slow down is rarely the thing worth slowing down, and it is also why neither of the two reductions measured for 0.9.18 changed a cadence at all: both removed work from inside a pass rather than making passes rarer, so what a session costs fell by about nine tenths with no latency given up anywhere. A change that does move a poll rate is a change to user-visible behaviour and belongs in this document.

The Decky-managed backend log is an operator diagnostic, not an unbounded request transcript. Backend RPCs and owned background operations emit structured lifecycle events with a short correlation ID, stable operation/event name, terminal state and duration. Successful high-frequency read/poll calls stay at debug unless slow; state-changing operations and meaningful domain transitions use info; expected provider/input failures use warning; unexpected failures use error plus bounded filename/line/function frames without locals. Catching at an operation boundary records context and then preserves the existing fail-closed result or re-raises after required cleanup; it never turns an exception into success. Dependency request-per-line logging is suppressed because it is both noisy and may contain transient signed URLs.

Every plugin-owned button, controller dismissal and choice records a stable action name in the bounded frontend support ring. Operation owners record starts and outcomes separately; an observed press never implies a committed mutation. Safe AppIDs, table SHAs, record IDs and provider identities make repeated rows distinguishable. Text edits record editing bursts without passwords, queries or cheat values. Surface mount/unmount and QAM visibility events cover navigation outside a button callback. The ring retains the latest 500 entries until the frontend reloads, counts evictions and is collected as `logs/frontend.json`; it is recent-session evidence, not a persistent recording of every session. Backend lifecycle logs remain the durable mutation evidence. The control inventory, routes and verification limits are in [UI action audit](UI_ACTION_AUDIT.md).

Persistent file writes use same-directory staging, flush/fsync and atomic replacement. Rename and unlink operations commit the affected directory entries, and a failure after authority moved is reported as DurabilityUnknownError rather than a clean refusal. Repair refreshes the UI even on that outcome; a later status-read failure never reverses a completed repair. Table deletion commits blob absence before metadata removal, and bulk cleanup syncs each retained owned directory before reporting success. Managed directories and critical inputs are checked for symlink substitution, path escape, ambiguity, size/count limits, and replacement during reads.

## 7. Cheat Engine identity and runtime copy

Stable v1 normally registers a manifest-pinned managed Windows Cheat Engine installation. New managed promotion selects the generic x64 executable directly: the official `Cheat Engine.exe` is a short-lived CPU dispatcher, while forcing the AVX2 variant would add an unnecessary host assumption. Older managed trees remain validated against the exact executable recorded in their immutable metadata until an explicit Reinstall promotes and registers the new choice. The release manifest fixes the clean HTTPS URL, allowed hosts, expected size, SHA-256 and the reviewed publisher's signing key; the repository/package never contains CE bytes. That URL is the only route while it serves the reviewed bytes. Nothing upstream republishes it - its path segment is opaque and changes between releases, and Cheat Engine's own version file carries no URL - so when it stops working setup rediscovers the current one: it fetches the pinned download page, accepts exactly one off-site download link from it, parses that download helper's own Inno metadata without running it, and accepts exactly one installer URL out of it. Ambiguity at any of those steps is a refusal. What the rediscovered URL serves is still held to the reviewed SHA-256, which is the only thing that authorizes an install: native extraction reads that exact artifact's format, so bytes it cannot parse could not become an installation however trustworthy their origin. The rediscovered artifact's Authenticode signature is checked against the exact reviewed publisher key anyway, with no certificate chain trusted in its place, because a different release from that publisher and a substituted file are both refusals that need different answers: the first says only the packaging is the problem and points at updating CE Decky or importing, the second says the artifact could not be trusted at all. The signature proves the publisher, never the version ordering, so nothing claims a refused artifact is newer. Host policy and byte bounds are never relaxed for the rediscovered route. A promoted installation records how it was obtained, what vouched for it and which hosts served it, and Advanced shows that; the working URL is not shown anywhere. When neither route produces an artifact, Home explains what failed and points at controller-accessible manual import, which remains a complete way to finish setup. The installer is a data container only: the backend validates the CE 7.7 loader/metadata CRCs, decoded metadata, each extracted payload SHA-256 and final PE files, then accepts only the exact owned staging tree after bounded regular-tree validation. It never executes the installer, invokes Proton, or accepts a diagnostic hash override. Managed setup reserves the CE identity/materialization boundary from before asynchronous download/extraction until terminal failure/cancellation or successful registration, so a long-running install/reinstall cannot race CE import, session preparation, private-runtime materialization, launch, or autoload. Native promotion is the irreversible commit point: cancellation drains that worker and, if promotion already won, the UI registers and reports the verified completion instead of claiming cancellation. Every terminal path drains its worker before removing the exact per-operation UUID staging tree. A completed operation remains resumable only until its exact installed identity is durably saved, after which the operation is consumed. A manually selected fallback executable must remain under `DECKY_USER_HOME`, look like a plausible Windows CE executable, and match its recorded SHA before use.

The selected installation is read-only source input. Public CE behavior loads autorun scripts from the executable directory, so bridge-enabled execution uses a plugin-owned private copy:

```text
ce/runtime/<versioned-aggregate-runtime-sha>/
```

The aggregate key binds the exact CE executable SHA, complete source-tree SHA, bridge SHA and runtime-layout version while keeping the Wine `Z:` executable path below the legacy process-creation limit observed on SteamOS. The manifest retains every constituent identity. Materialization accepts regular files only, rejects Windows/Wine-colliding paths and reserved bootstrap/bridge paths, enforces file and byte bounds, fingerprints the complete source tree, verifies the copy, and never updates an immutable runtime in place. Because CE enumerates `autorun/*.lua` with unordered Win32 `FindFirst`, the private copy preserves the source `main.lua` under a reserved name and installs a generated `main.lua` that loads the exact bridge before the untouched source script and shipped autorun directory. The registered installation remains unchanged.

Attached execution suppresses Cheat Engine's Win32 application-owner window and its normal forms before the first main-form map so launching a table cannot retain game activation, audio or controller focus. The bridge preserves CE's own main-form initialization handler; user-defined forms created by explicitly authorized table content remain table behavior, not hidden process or anti-cheat evasion. Suppression covers the forms Cheat Engine assigns to its application, which a message dialog is not: on the target one such dialog sat over the game while the form sweep reported everything hidden, and the game kept its audio and its controller but lost its picture. A window this process owns and holds in the foreground is on screen whatever it is made of, so it is dismissed with a close, which Cheat Engine treats as cancelling. That is an answer nobody gave, so it is never silent: the count and the last caption are published and shown under Advanced. A window the sweep cannot put down at all is reported as a state and not as a total: the sweep runs on a timer, so one window nothing can hide fails once per tick, and the count of those attempts says how hard it tried while a separate flag says whether a window is over the game right now, which is the half that can go back to no when the window finally goes down. Taking the window away is only half of it: a game that lost the foreground to it has minimized itself, and it stays minimized once the window is gone, drawing nothing while its sound and its controller keep working. Nothing outside the game can undo that, which was measured: mapping and activating the window through the compositor changed nothing. So the attached game's own windows are asked to restore, from inside its own Wine session. The windows are resolved by walking the system's own top-level window chain and keeping the handles the exact opened process owns, because a caption is neither an identity nor unique: on the target the game's own second window caption resolved to a window belonging to a different process entirely, and a caption lookup answers with that same foreign window every time, so the game's real window by that name could never be reached through it. The request goes only to a window Windows itself reports as minimized, because for one that is maximized instead the same request means "back to windowed size", and a game that stays up when it loses the foreground would be taken out of fullscreen by the very thing meant to help it. Being behind something is not being minimized, and no proxy for it is safe. Cheat Engine's own window API cannot answer this, but `IsIconic` can and Cheat Engine can reach it: `executeCodeLocalEx` calls a function in Cheat Engine's own process by symbol name, which is how Cheat Engine's own shipped autorun scripts call `DrawIconEx`, `ExtractIconA` and `ntdll.RtlGetVersion`, and the call answers for any window in the session rather than only Cheat Engine's own. The mechanism is proven before it is trusted, twice: at load against a window handle of zero, which is not a window and therefore not a minimized one, and again against the main form once it has a window of its own, which exists and is never minimized. An answer of "minimized" to either is not this question being answered, and refuses the mechanism for the session. Where it cannot be established nothing is sent at all, the resident status publishes which call answered or that none did, and Advanced states it, because a game left dark has to be attributable to something. The request is posted rather than sent: `SendMessage` does not return until the receiving window's own thread has handled the message, and that thread belongs to a game which may be loading, hung, or not pumping at all while it is minimized, which would stop the bridge's timer with it and take the heartbeat and every runtime command down for as long as the game took. Nothing here reads the result, so `PostMessageW` is resolved from the same local symbol table and used instead, and only a post the call reports as queued counts as the window having been asked. Each window is asked once until Cheat Engine puts up another window, since a game that came back maximized would be sent to windowed size by a second request. Both halves are one capability: seeing that a game is minimized and having no way to ask it back is reported exactly like not being able to see it, because the outcome for the game is the same. It is deliberately slow and deliberately narrow. Hiding runs first and only a window still in front a sweep later is closed; a window this process owns for itself is never in the foreground to begin with; anything hiding reaches is never closed, which is proven rather than assumed, because Wine leaves the foreground on a window that was hidden rather than destroyed: the candidate is closed only when it is provably none of the forms Cheat Engine assigns to its application, which is where a Cheat Engine tool window and a form an authorized table created for itself both are. Each form is identified by its window handle, or failing that by its caption, exactly as the main form is, and closing the main form would end the session, so a window that cannot be told apart from any of them is left alone; and one window is answered once, because a dialog that ignores the close must not be reported as a thousand dialogs.

## 8. Table and archive pipeline

Every input path converges on the same pipeline:

```text
local file or provider artifact
  -> bounded staging and SHA-256
  -> direct CT, safe ZIP, or host 7-Zip inspection
  -> explicit candidate selection when an archive has multiple CT files
  -> controller password input when the selected member is encrypted, including a single-member archive
  -> bounded XML/static inspection
  -> durable catalogue metadata
  -> immutable table blob
  -> optional provider provenance
```

An archive that opens correctly and holds no `.CT` ends the same way a damaged table does, and is said to be what it is rather than damaged: the transfer and the archive were both fine and there is nothing in it, which is a property of those exact bytes. Every other archive failure keeps the ordinary path, because a 7-Zip without the handler for a format and a member that could not be read are conditions of this device or this read rather than of the file.

A file the source no longer has leaves no content to key on: nothing was downloaded and there is no digest. It is recorded by the provider row instead, in the same list, because to the user it is the same statement about the same row and clearing it is the same press. A source that answers about one exact artifact that it no longer has it ends that acquisition as a retired row rather than as a provider outage: the source is working and this file is gone, so it is not counted against the source as unavailability, it is not retried, and the catalog stops offering those exact bytes exactly as it does for a table that proved damaged. A source that serves over plain HTTPS says this with 404 or 410; a source whose own client contract answers in its own vocabulary raises it from the adapter that reads that vocabulary, which is the only place it is understood. The user is told which source answered and that the page offering the file is still there while what it points at is gone; the source's own code and wording reach the log and the provider diagnostics, where the failed download is counted.

A `.CT` is checked for well-formed Cheat Engine table structure at the inspection step, not only at import: a table can match its advertised SHA-256 exactly and still be damaged at its source, and target evidence includes a published Playground table that closes a `CheatEntry` no open tag matches. Such an artifact is reported as a damaged table rather than a parser fault, retires its acquisition, and is not counted against the provider that delivered exactly the advertised bytes. The catalog stops offering those exact bytes while the search results they came from stay cached, because a retry can only repeat the same provider countdown and the same outcome. An explicit fresh search clears that mark: a provider can replace a damaged upload with a fixed file under the same identity. CE Decky never repairs untrusted table content.

ZIP is handled in-process. For 7-Zip formats, `.7z` and `.rar`, discover `7z`, `7za`, or `7zr` once, retain the absolute path, run without a shell, list before extraction, select one member, bound actual output, and validate again after extraction. Encrypted 7-Zip formats are disabled in the current production design because a command-line password can leak through the process list. `.rar` needs a handler only the full build carries, so the resolved binary is asked once which formats it has, and a search on a device whose 7-Zip lacks it drops those rows rather than offering a table that costs a provider countdown and a download to be refused at the archive.

Import commits catalogue metadata before publishing the blob. A failed or interrupted promotion therefore leaves a visible unavailable entry that can be re-imported or removed; failed metadata publication never deletes a pre-existing shared blob. Startup performs bounded reconciliation of legacy blobs without metadata, accepting only exact-SHA validated CT bytes and naming recovered entries by digest without inventing provenance or arrival dates. Recovery grants no execution consent.

Before session preparation, re-hash the stored blob with `TableStore.verified_blob()`. UI presence and size checks are not execution-integrity evidence.

## 9. Game identity and Proton eligibility

The profile key is the exact Steam library AppID supplied by Steam, including non-Steam shortcut IDs. Store display name, shortcut executable/start directory/options, compatibility metadata, aliases, and an explicitly confirmed target process.

Provider matching may normalize punctuation, compact letter/digit forms, Roman numerals, bilingual labels, and cosmetic editions. It must guard sequel numbers, release years, remake/remaster qualifiers, and ambiguous top matches. An ambiguous match requires confirmation and the provider-specific binding is then persisted.

Search eligibility and launch eligibility are separate. A game can use table search/import while launch integration is disabled. Proton launch states are:

- `confirmed_proton`: current metadata proves a Proton-family tool;
- `not_proton`: current metadata proves a native/non-Proton launch;
- `uncertain`: metadata does not prove the actual route.

An empty compatibility-tool name is not a verdict. Broadening the heuristic requires recorded AppDetails behavior for Windows-only, Linux-only, dual-platform, forced Valve Proton, custom Proton, and non-Steam examples.

## 10. Cheat Engine launch

CE Decky starts Cheat Engine itself, as a process it owns, and needs no Steam state at all. **CE Decky never writes Steam launch options and never edits Steam configuration.** There is no sidecar route: an earlier design carried Cheat Engine into a game through `PROTON_REMOTE_DEBUG_CMD` and a Steam launch-option write, and 0.9.0 deleted that integration together with its ownership/recovery journal, because attaching to a game that is already running serves every case it was meant to cover.

The backend starts the private extracted Cheat Engine runtime itself through an exact installed Proton tool and owns the launcher process group plus durable descriptor identity. The verb is chosen by mode and never mixed: the self-test uses the ordinary `run` verb in a plugin-owned prefix, so Proton performs its own prefix setup; an attached launch uses `runinprefix`, which Proton implements as `run_proc([wine_bin] + argv)` after `init_session(update_prefix_files=False)`, the same invocation it uses for `PROTON_REMOTE_DEBUG_CMD` and one that explicitly does not rewrite the game's prefix files. The launch environment sets the exact prefix/client/AppID/descriptor values and a Gamescope `DISPLAY` read from the Steam user's protected runtime environment and corroborated by that user's live X11 socket; inherited Proton/Wine/Steam identity values are removed first. Executable, descriptor and table Wine paths are rejected before launch if they cross the supported Windows process-path bound.

Two modes share that supervisor:

- **Self-test**: an isolated plugin-owned compatibility prefix, a synthetic session with an empty reviewed `.CT`, no game and no Steam state. Success means the resident bridge reported a heartbeat for that exact session; the supervisor then retires every client in that exact owned prefix through the selected Proton wineserver and verifies cleanup. This is the first-launch proof a user or an agent can run before anything else exists.
- **Attached**: the running game's own compatibility prefix, so Cheat Engine shares that game's wineserver and can see its processes. The prefix is resolved independently from Steam library metadata and must equal the value the running game reports in its own environment; the Proton identity is taken from the running game's `STEAM_COMPAT_TOOL_PATHS` rather than chosen, and so is its X display. Gamescope runs more than one XWayland server and Steam and the game do not share one, so Cheat Engine joining the game's prefix and wineserver on the session's display makes Wine's X11 driver operate on window identities from another server and the process ends on the Xlib default error handler. Ambiguity, disagreement, or an unobservable identity fails closed.

Cheat Engine can be started while a game is already running and the intended stable-v1 workflow stops only the descriptor-bound CE client before starting a different prepared session. Cheat Engine is stopped by its exact descriptor inside the game's shared wineserver; prefix-wide wineserver termination is forbidden there because it would end the game.

Ownership and lifetime are deliberately not the same thing. A self-test is a bounded transaction and is always stopped, including on cancel and plugin unload. An attached launch is the user's running tool: a Decky reload or plugin update releases the supervising task but must not end Cheat Engine mid-game, so it writes to an owned log file rather than an inherited pipe and records its exact identity durably; inability to persist that identity aborts the launch. After the plugin loads again, that record is reclaimed only when the live process environment still carries the same descriptor path and SHA-256, which is what makes a recovered process controllable rather than orphaned. A missing/reused PID becomes a confirmed exit, while unreadable process evidence or malformed ownership state stays blocked and is never treated as proof that the process is gone. An owned Cheat Engine ends itself when the game it was started for exits, and the program it watches for that is the one the session is pointed at now rather than the one the launch began with: a retried attach moves the session to another program and deliberately leaves the profile alone, so watching the profile's name ended the launch when the program the user moved away from exited, in the middle of the game they moved to. A session that cannot be read leaves the launch watching the name it started with, which is what it watched before, and a name nothing has ever been seen running under can still only be ended by the whole game being gone.

## 11. Runtime session and bridge

Session preparation creates an immutable session-local table snapshot and data-only descriptor/control/status files under an AppID and UUID-specific directory. Identity binds:

- library AppID;
- session UUID;
- exact CE executable SHA;
- exact table SHA;
- descriptor SHA-256;
- target process.

Mutable bridge files use a strict percent-encoded line protocol with bounded fields and counts. The Lua bridge does not call `dofile`, `loadfile`, `loadstring`, or `load` on them. Host SHA-256 is authoritative; CE's documented `md5file` check is defense in depth against a descriptor race, not the trust anchor.

CE Decky keeps a durable record of exact tables that were proven not to work, keyed by the table's SHA-256 and holding the reason, the filename, the game and the version that game's own executable declared at the time. Four things record one, and each entry also carries which of them it was, because a user acts differently on each: Cheat Engine running a cheat and the record coming straight back off, which is what a table written for a different build of the game does and may stop being true when that game updates; a download whose bytes are not a usable table at all, which never stops being true; an archive only 7-Zip opens with every member of it encrypted, which is terminal for those bytes here and which the user can answer by re-packing it as a zip; and a file the source says it no longer has, which is a fact about that source's page rather than about this device. The reason beside them is a sentence assembled from what Cheat Engine or the archive layer said, so it is what a screen with room shows and never what a screen classifies by; the cause is recorded where it is known, by the route that writes the entry. A cause that cannot be read reads as the plain statement that the user recorded the table as not working, and the entry is never refused over it: the record protects an import, and a label it cannot make exact must never cost it that. Every entry also carries the game it was tried on, which travels with the press that produced it and is named from the profile store rather than from a display name a screen passed in, because the list spans every game and is read months later: a bare archive name or a provider row answers nothing about what a table was for. A game that cannot be read is an entry with no game, never a write that did not happen. The record has one on-disk shape rather than a reader carrying every shape it has passed through; a file older than that reads as unreadable, which refuses nothing and is repaired by the same **Clear all** as any other unreadable record. The record greys the table in search, refuses to import those bytes by any route, never withholds a usable copy already on this device from the row that produced it, and is summarised under **Advanced → Tables that did not work** as how many tables are refused, when the newest was recorded, and what the record spans, which is the one thing about it that cannot be read off the entries from a screen they are not on: the game where every entry is one game's, how many games where they are not, how many belong to no game this device could name or never produced a file of their own, and the day the oldest was written. Its **Review** screen lists every entry with its reasons, a page at a time, and clears a single one or all of them. A single entry stays clearable however long the record is, because a table refused for an older build of the game becomes correct again when that game updates while a download that was never a table does not. It is advice and a refusal to re-import, never a trust decision: it authorizes nothing, and a table already selected keeps working until the user changes it. The home panel's table row carries two controls, **Search** and **Manage**, because a 300 pixel panel row that already holds a filename has room for two. Search is the online route; everything else about which exact table this game runs is behind Manage, which is where a table is chosen, where a local `.CT` or archive is opened, and where a stored table is removed. Manage withholds **Use** from a table another game owns: a cheat table is written against one game's code, and the press does more than fail, because it associates the table with this game before the review opens and cancelling that review does not take the association back. Ownership is the test rather than which of the two groups the row is in. A table this device holds that no profile claims keeps the press, because after a recovery that discards the profile store it is the only route back to bytes the device still has: Search needs a provider row and Local file needs the original file, and offline there is neither.

Manage is a device-wide library manager and opens without a selected game. Without a game it lists every local table and its holders, including removed games; selection and local import require an explicit game choice. With a game selected, Manage opens with the file row, because that is one line, is the only route that works on a device holding nothing, and would otherwise sit below a list nobody scrolls to the end of. Below it is one list of tables with one page budget for the whole screen, one pager and one filter over all of it: two lists paged separately put twice as many rows on a screen that fits one page. The order carries what separate headings would: the table this game currently has selected comes first, because the panel sends the reader here to authorize exactly that one; then the rest of this game's own; then every other catalogue entry the device holds, marked where that boundary falls. Missing or damaged files remain listed for removal or re-import, with Use disabled. An active filter stays visible even when deletion reduces the list below one page. Choosing one associates it with the game selected now and opens the ordinary review screen, where the exact SHA is authorized again; nothing guesses which game a table used to belong to.

Reaching a stored table matters because the association between a game and a table is what the two supported recoveries discard: deleting the plugin's saved setup keeps `tables/` and removes the state beside it, and discarding an unreadable profile store starts an empty one. Both tell the user their tables are kept, and before this the only routes back were a provider result that still mapped to those bytes and the original file on disk, so an offline user with neither held the exact table and could not name it. Revoke withdraws authorization, disarms Auto-load, retires the exact prepared session after owned Cheat Engine is stopped, and detaches the selected SHA. One durable profile save archives the withdrawn consent with the table preferences, preserves library history and local bytes, and clears the current binding. It operates on durable AppID and exact selected SHA even when the game is no longer installed, and an identical retry is idempotent. Selecting that table later still requires fresh exact-SHA consent.

Each row is described from one provenance record: the release the provider advertised for those exact bytes, which is what search offered them under and what tells one revision from another, then how many records the table holds, the source it came from, the date those bytes arrived, and the exact digest and size. A release is labelled as its source wrote it, so a tag that already carries its own marker is not given a second one, and a release that is a name rather than a number is left alone. Where a provider publishes no release, one is read from everything that source does publish, which differs by source and is best effort rather than a uniform rule. The file's own version is the fallback, for a local import and for anything recorded before the advertised one was tracked, and a row claims no version when there is none. The date is when the bytes arrived: a download records that in its origin, a local import records it as the arrival stamped by the table store, and anything imported before that was tracked carries no date rather than borrowing a file's timestamp.

Removing a table is the only per-table removal route, and it is permanent: **Advanced → Prepare for removal** can still take the whole tree in its widest scope, but this is the only place one table goes on its own. Those bytes may be the only copy, which is exactly the case the offline route exists for, so the confirmation says that rather than promising the table can be fetched again. It takes two presses on the same control with the row saying what the second does, never a window over that window, it never takes the focus from the press that uses a table, and moving away from the row disarms it. A table any game currently has selected offers Revoke with in-row confirmation naming its holders. Confirm withdraws the exact confirmed holders before Delete becomes available; partial withdrawal refreshes the remaining holders and keeps the local file. The row shows up to three holder names in ascending AppID order, clipped to 48 Unicode characters plus an ellipsis, with the remaining game count as (+N), including when the current game shares it; deletion is gated by the full holder count, and games with identical names still count separately; the backend refuses that case regardless, because the screen holds a snapshot and the answer can change under it. Removal takes the bytes first and the record last, so a failure leaves a table that lists as missing its file rather than storage nothing can name, and the row leaves the open screen only when the removal actually succeeded. Focus then moves to the next surviving action, the previous one when necessary, or Back when none remain.

Answering the refusal dialog with **Stop using it** is that change: it withdraws the table's execution authorization and then clears the game's selected table, so Home stops offering the table, its launch and its cheat configuration for a table just proven not to work. The panel that is on screen after that answer opens with the ring on **Search**, whichever of the routes above put the question, because looking for another table is what is left to do about a game whose table has just been retired: Home ordinarily opens on **Advanced**, and the panel the question was asked from is usually gone by the time it is answered. The request outlives that panel and is spent the moment the ring lands, so one answer moves it once. The same Revoke command atomically disarms Auto-load and detaches the selection with the consent withdrawal. The bytes stay in the game's library and the table's own pinned controls, saved values and startup actions stay archived against its exact SHA, so clearing the mark and selecting it again restores all of it. Keeping the table is equally real and writes nothing, so a marked table can still be the selected one, as it can when the same bytes were marked while another game was playing them; Home's table row and the list of tables already imported for a game both say a table is marked as not working rather than presenting it exactly like one that works. A record that cannot be read blocks nothing.

The bridge starts from the private runtime autorun directory, reads the descriptor path from owned launch environment, loads the exact session table through CE's own documented `loadTable`, waits for the target process, attaches with public CE APIs, applies startup actions, and maintains a bounded heartbeat/control loop. The launch does not name the table on CE's command line: CE opens one from there only once its main form is shown, and CE Decky never lets that window map, because a mapped Cheat Engine window takes the running game's audio and controller input with it. A table the bridge could not load is published as such rather than left to look like a table with no usable records.

Generation zero is startup-only. Runtime command generations are consecutive, replay-protected, and preserved across frontend reload until acknowledged. Frontend success requires the exact generation, expected MemoryRecord identity, exact descriptor/session identity, and a positive bridge result; a negative ACK remains a failed operation even when it carries useful current state. Status for another AppID, CE SHA, table SHA, descriptor SHA, session UUID, or unauthorized target process is rejected. A stale heartbeat means disconnected; suspend/resume grace remains a target measurement.

Bridge connectivity and target attachment are separate states. `list_processes` and `retry_attach` remain available to a fresh/current but unattached bridge, while `query`, `set_active`, and `set_value` require a positive attached PID both at the host mutation boundary and again in the CE-side bridge immediately before execution. Host RPCs revalidate unique actionable record IDs and control types against a fresh exact-SHA table inspection.

The retry-attach protocol identity is an unambiguous `.exe` basename, not a PID. QAM filters bridge process rows to valid basenames, collapses case-insensitive duplicate names while reporting the observed PID count, and sends only the selected basename; custom profile targets are rejected before save if they contain paths or invalid executable-name characters.

A current prepared session is not silently superseded while its bridge heartbeat is fresh or clock-skewed. Clock uncertainty fails closed for replacement and retirement. The single exception is evidence, not a relaxation: when CE Decky started that exact session's Cheat Engine process itself and has observed the owned process group exit, a heartbeat written before that confirmed exit cannot belong to a live bridge and no longer blocks replacement. A status write newer than the confirmed exit still fails closed, and a session CE Decky did not launch is never affected. Profile deletion requires the current prepared session to be explicitly retired first; stale-heartbeat sessions may be replaced/retired while immutable session evidence remains.

## 12. Provider architecture

Provider networking is production code, developed and tested off target. Adapters discover normalized metadata while one shared cancellable transport owns HTTP, redirects, staging, hashing, and validation.

Every provider queries and scores candidate titles against the name the library shows for the game, never against its executable. Steam's own name for a library game is authoritative, and a user who adds a non-Steam game normally corrects its name, while an executable is named for whatever the build happens to be: an executable named after a single word of its own title yields that word as an alias, and such an alias scored an unrelated game that happens to share the word above the provider floor, filling a search for a recent game with results for one released years earlier. A localized or otherwise unhelpful name is corrected in the search field, which is explicit and reviewable, rather than by silently widening the query. Search identity is ranked, never merged. The name the library shows is the only source used while it finds something. A search that returns nothing it can download is retried once against the directory the game was installed into. Deciding this on results rather than in advance is what keeps a folder that names a different game, such as a mod installed inside its base game's directory, from ever outranking the entry the user chose. Only the launched program's own path is read, never the arguments after it, so an emulator launcher contributes nothing; build output, library roots and packaging words are not titles. An entry carrying no usable name at all falls back to its directory and then to its executable, because the alternative is no searchable identity.

A parsing failure never costs more than what could not be parsed. Everything a provider says *about* a table, its version, size, author, date, download count, notes and recorded origin, is publisher-authored description around the one thing that makes a table obtainable: the link, its filename and its HTTPS source page. A described value that cannot be read or validated is dropped and the artifact stays offerable; a row whose own identity is unusable is skipped alone; a page or topic that cannot be read at all costs that page, never the provider or the other pages already fetched; a cached row that cannot be read costs that row, never the rest of a stale answer; and provenance that cannot be recorded or re-read never withholds a table whose bytes are downloaded, validated and stored. This holds for every provider, and for a source that redesigns its markup without warning. It also holds before a page is fetched: an optional field a listing publishes about a post, such as when it was last modified, may narrow what is worth fetching but never decides on its own that an artifact is unavailable. Where such a field and the validated route both say something about the same post, neither withholds it by disagreeing with the other, and the post is skipped only when everything known about it agrees that it is out of range.

An index a provider publishes across several pages is cached only when every page it declared was read. One page failing is a degraded answer for the search in front of the user, which still uses what it has; recorded as the whole index it would silently remove everything that page contained from every later search until the cache expired, with nothing saying so. Such an index is also read structurally rather than by pattern, because a document that stopped early otherwise yields the part that arrived and looks like a shorter index rather than an incomplete one. It does not relax any check that decides what the bytes are or whether they may run: digest verification, host and redirect policy, archive and table validation, executable-content classification and exact-SHA consent all still fail closed, and a listing or index that cannot be read is a failed source because no artifact was found to preserve.

What could not be read is counted rather than hidden, because a source that quietly stops being readable otherwise looks like a game with no tables. Each provider carries two counters in its diagnostics: unreadable pages, the critical kind, where nothing on that page can be downloaded and a wholesale schema change is the usual cause; and partly-read rows, where description was dropped or a single row skipped while tables stayed obtainable. Both are shown per provider under **Advanced / Debug**, and one bounded line per provider per search, with a sample of reasons, goes to the log.

Diagnostics retained from a provider that is no longer in the registry are support history, not current provider state. Advanced labels such a row as retired and historical; it never leaves an old error looking like a failure of a provider the current version can still query.

Every source is on by default and the user may switch any of them off. **Advanced -> Table sources** carries the count and the totals, and a screen of its own lists each source beside what it has actually done on this device: searches answered, tables produced, downloads finished and failed, pages that could not be read, rate limits waited out, and any wait the source itself asked for. That evidence is why the switch is worth offering, because a source is switched off after it has been seen failing or finding nothing, and a row of counters is the only thing that can say which. A source that has never been asked for anything says so rather than showing zeroes.

Switching a source off stops it completely rather than only skipping its own search. It is not queried, it is not read when another source's page names an exact page on it, its rows are no longer re-served from the search cache, and a row of its own already on screen can no longer start a download. Nothing already downloaded from it is affected, and nothing about the choice is a trust decision: it authorizes nothing and refuses nothing that consent already governs. The choice is durable, reversible per source, and resettable as a whole, which is also the repair for a record that cannot be read; while it cannot be read every source is searched, because a preference nobody can read must not be able to make the plugin find nothing with no visible cause.

A source is credited only with what it served. A page one source publishes can name the exact page a table lives on at another, and those rows carry the second source's identity, so they are counted against it, as a read through a link rather than as a search nobody ran. The counters are what the switch is decided on, and one source's rows appearing under another source's name is the one way they can mislead.

Nothing here invents a measurement. A source that has never been asked, and a whole counter record that could not be read, both have no counters, and neither is shown as a row of zeroes: a zero is a measurement, and stating one that was never taken is a stronger claim than saying the record is unreadable. That record is also not repaired by using the plugin, because every path that writes to it loads it whole first and every caller ignores a failed load so a broken counter can never fail a search. Advanced therefore offers to replace it, and says so rather than promising that searching will fix it.

A search names the sources it did not ask. A switched-off source appears in the per-source line as off instead of being dropped from it, and a search with every source off says so in a sentence rather than reporting that this game has no tables: those two answers are indistinguishable otherwise, and only one of them is about the game.

Artifact versions are shown only when the publisher marks a number as a version (for example `v5` or `Version: 1.2`) or puts a bounded dotted release token in the filename itself (for example `Table_1.0.5.CT`). Bare attachment metadata is not guessed: decimal file sizes, download counts and long build identities must never appear as synthetic versions.

Planned initial sources:

1. local import;
2. FearLess Revolution through its own table-forum listing, which is indexed rather than searched, because its search route challenges anonymous HTTP;
3. Playground catalog discovery through the game's own `table` category with anonymous direct acquisition;
4. The Cheat Script through its declared sitemap and anonymous Yandex Disk public resources;
5. GitHub through its own repository index, and as the exact `github.com/<owner>/<repo>` source another catalog exposes. CE Decky contains no hard-coded per-game registry: a repository is found by searching the index at run time, and is offered only when it actually carries a table;
6. VGTimes through the game's own table listing, with anonymous acquisition through the site's own download chain.

GitHub is not a catalog of games, so discovery is what it lacked rather than acquisition. An anonymous client gets ten repository searches a minute and sixty other requests an hour, counted per device, and code search answers it not at all, so a table cannot be found by file extension and the repository index is the only route. A search spends a fixed small slice of that budget: a bounded number of queries that ask the index itself to exclude forks and archived repositories, then a bounded number of ranked repositories. Each normalized repository-index answer is cached by exact query for 24 hours, with at most 32 recently used queries retained. A stale answer remains an offline fallback for seven days only when refreshing that exact query fails; release and tree reads stay live, so the cache never hides a newly published table in a repository it already found. A repository is scored on its name with the words the query supplied removed, because every candidate carries them and they are spelled differently enough to decide the order on their own. Repositories that are Cheat Engine itself, a general table dump, or that name multiplayer cheat techniques anywhere in their name, description or topics are dropped rather than offered and refused later. That last filter names only techniques that are unambiguous on their own; a word an ordinary single-player table would also use, such as unlocking everything, is not evidence, and a word that only means something once its object is named, such as bypassing, counts only when what is being bypassed is named with it. A repository is offered only when it carries a release asset or a table committed in its tree, which is a fact about the repository rather than a guess about its name: the index returns repositories whose whole content is a README promising a table. Releases are read first, because that is where tables usually are, and the tree is read only when they carry none, so an ordinary repository costs one request rather than two.

The two GitHub routes differ in what integrity they can offer, and neither is trusted without one. A release asset may advertise a SHA-256, which is checked against the downloaded bytes exactly as any other provider digest is. A file committed in a tree advertises git's own object name instead, which is not a digest of the bytes alone but is exactly defined and reproducible, so it is verified rather than accepted. That name is never presented as a content digest: nothing that identifies a table by SHA-256 keys on it.

VGTimes has the cleanest discovery shape of any source here. The game is its own path segment and tables have their own listing, so `/games/<slug>/files/cheats/tables/` is a table-only answer and no entry has to be opened to find out whether it is a table rather than a trainer, a save or a save editor. The game index comes from the site's declared sitemap, is cached and ranked locally the way Playground's is, and a search reads a bounded number of ranked games and a bounded number of their entries. Each item page publishes a schema.org block carrying the title, the category that confirms the entry is a table, the author, the date and an exact byte count, and the report linked beside it carries the artifact's SHA-256, so the digest is known before the user chooses the row. The exact filename the site will serve is read rather than derived: a row that cannot say what it would fetch is skipped and counted rather than offered under a name invented for it.

Its acquisition is the site's own chain, and nothing about that chain is written down in CE Decky. The page declares this client's address, its group, the file server it will use and the bundle its client is built from; the bundle names the module a files page loads; that module carries both routes, the fields each is sent, the countdown and what its own client does with every refusal code; and the challenge answer states its key derivation, the header it is keyed by, the image fields it wants read and the shape of the object it expects back. A route or a parameter frozen in the adapter would be a snapshot of one day's site, and the day it moved the adapter would send a confident wrong answer instead of reporting that it no longer understands the contract. The countdown the server enforces is waited out and shown as a countdown rather than left looking like a stalled download. Nothing from the site is executed: the challenge script is unpacked by substitution over the dictionary it carries with it and read as text.

The object that chain builds has one slot a browser fills with an automation probe. CE Decky is not a browser, computes none of it, and sends that slot empty, which the site serves; there is no code path that fills it, and the URL builder refuses a non-empty one. This adapter never describes this client as something it is not.

A guest may have one download open at a time on that source, and the site says so in its own words rather than leaving it to be discovered. CE Decky therefore holds a single download in flight per provider where the provider declares that rule, waits rather than treating the resulting refusal as a failure, retries a bounded number of times reusing the token it already holds, and finally reports the sentence the site would have shown. A refusal that asks for the waiting page again is followed; the site's download queue is a flow CE Decky does not implement, and a file the site says it does not have is not asked for twice.

Open Cheat Tables was one of these and is not any more. Every route this needs from it answers with a site-wide challenge rather than a page, measured with this plugin's own network client, and the only routes that do answer carry no titles to build an index from; the adapter also reached it through a search route that site's own `robots.txt` disallows, which this project does not do.

FearLess discovery never depends on its challenged `search.php` route. Its
public table-forum listing exposes a bounded page count plus topic titles and
IDs, so CE Decky refreshes the leading listing pages during a search, resumes a
bounded local title index in the background, and shows indexed/total page
progress in QAM. What that index holds is said where it decides what a
search can find: the row that heads the results on **Search / Download**
carries it under that row's own press, because a table on a listing page this
device has not read yet is absent from the copy rather than from the source,
and searching again once the index has caught up is what finds it. It is read
from the search's own answer, which already reports that source's index state
on the row it reports for it, so the screen spends no call of its own on it
and says nothing where that source was not part of the search. A page never read is told apart from one only due to be read again, because an aged page is still in the copy and still searched, and only the first kind hides a table. The answer is as old as the search, and a reopened Search shows the one it kept: the wait a source asked for is counted down from when it asked, and counts older than a minute say they are that search's rather than the copy as it is now. The index contains no table bytes, attachment URLs, cookies or
session IDs. A topic the forum has sorted to the end of its own listing with a
leading lowercase `z` is scored and shown under the game's own name: the marker
is the forum's ordering rather than part of the title, and carrying it into
scoring put the topic far below the floor a topic has to clear to be fetched at
all, so those games returned nothing from the source that had them. Only the
lowercase marker is one, because a real game on the same listing is titled
`Z Remastered`. A multi-page stride is accepted only when numeric pagination links
explicitly relate page numbers to offsets, every such relation agrees, and the
result is possible under the listing's advertised page and topic totals. Page
zero establishes and changes that geometry. A later page may reuse the proven
stride when phpBB renders its current number as a non-link and therefore exposes
no independent stride; its `Page N of M` identity and totals must still fit the
known geometry, and any explicit stride must agree. A single-page listing
persists with only offset zero and no invented stride; ambiguous page-zero
pagination costs that listing page instead of creating an index with silent
holes. Search reads page zero before calculating the other leading offsets, so
a changed stride takes effect during the search that first observes it. Search
scores local topic titles first and fetches only the bounded
best-matching topic pages needed to discover their current attachments. A first
search may therefore return fewer FearLess results while the index is still
being built; **Search again** uses whatever additional pages are complete.

Direct backend downloads require HTTPS, explicit provider host policy, redirect revalidation, public-address checks, bounded streaming, content validation, narrow retry behavior, and verified TLS. CE Decky accepts the system resolver as the trusted resolver-to-connect platform boundary; it still rejects a URL if any preflight A/AAAA answer is non-public and repeats validation on every redirect. HTTP 403/challenge marks that provider unavailable for the query, never bypassed; HTTP 429 causes persisted cooldown. That holds at every read a provider owns, not only at its first: a challenge answered by one of its pages stops the rest of that provider's reads for the query and reports it as unavailable, because skipped page by page a provider challenging everything that matched returned an empty list, and an empty list read as a successful search of no results. Rows already obtained before the challenge are kept. That covers every read a provider owns, including the listing that decides which of its pages are worth opening and the crawl that builds its index, because the pages either would go on to ask for are the same challenged site. A source reported as unavailable is also recorded against itself once, by whichever of the job or the search observed it, so the screen that exists to say which source is failing is not reading a value nobody wrote down. A search that finds a provider already inside such a cooldown is not a failure of that provider: nothing is contacted, so nothing is recorded, and the deadline that produced the skip survives it rather than being overwritten by it. A source that answers partly and then stops, from a cooldown it reaches with results already in hand or a limit part way through, reports both at once: the rows it obtained are kept and the source is still reported as unavailable, because reading every returned list as success cleared the deadline that had just been set and hid the outage behind a result count of zero. Each source also has a bounded share of the wall clock, and it is one share for the whole search rather than one per attempt: the retry against the install directory spends what is left of the same budget, because two passes each given the full allowance is the same source holding a controller-visible search for twice as long. A source that has not answered within it is unavailable for that search, and the sources that did answer are delivered rather than held behind it. A source that answered partly and then stopped is reported as partial, with the count of what it did return, rather than as one that found nothing. A page one source links at another is read on the owner provider's terms, honouring its cooldown and recording its refusal against it, while the linking source's own row stands either way. Because that row stands, the linking source discards the failure, so the record kept against the owner is the only trace such a read leaves: it counts the error and names it, and stays narrower than a search failure, because no search of that provider happened, an optional read somebody else's page asked for is not evidence that its own search is broken, and a failure that names no deadline must never write one.

A URL already known while a search runs is held to what the transport will structurally accept, HTTPS with no userinfo on the default port at an exact allowed host, before a row promising a direct download is built from it; resolution and public-address policy stay in the transport, because they need the network and can change between search and download. An entry in a provider's own index is held to the same rule before it contributes identity: an index document must be the document that was asked for, and an entry from another origin is not this provider's, whatever its path looks like. A row whose exact size is already known to exceed what any download route will transfer is not offered. Only an exact size decides this; a described or rounded one stays governed by the streaming bound at transfer time. The source is still reported as unavailable for that query, so it stays distinguishable from a game with no tables. The QAM presents only results CE Decky can download itself; a challenged or browser-only source is counted in the visible per-source summary so a provider that quietly stops working stays distinguishable from a game with no tables.

The Cheat Script discovery follows only the Blogger sitemap its `robots.txt` declares. Search, category, tag and feed routes are disallowed and never requested. Post slugs carry game titles, so all sitemap entries are ranked locally and only the bounded best matches cause a post fetch. Posts before the publisher's measured 2024 migration to Yandex Disk are excluded by sitemap date; an older post edited later may still be checked and then dropped if it contains only the unsupported legacy Mega route. A supported post keeps only its stable public-resource key in the in-memory search snapshot. The documented anonymous Yandex public-resource API supplies the exact served filename, byte count and advertised SHA-256 before the row is offered. Its transient download URL is requested only after selection and stays backend-only. The current downloader hop refuses the third-party post Referer and redirects to a per-resource `s<token>.storage.yandex.net` shard: CE Decky sends no Referer for that artifact, accepts only that bounded HTTPS hostname grammar from the trusted downloader response, and converts the one returned hostname into an exact per-acquisition allowlist before the shared downloader starts. Both transient URLs are discarded after use. Invalid descriptive metadata costs only that value or row, while URL, host, size, digest, archive and table validation remain fail closed.

Playground discovery uses its public sitemap to resolve the game, then the game's own `/<slug>/cheat/table` category listing, whose table entries are the only pages fetched: the same section also holds trainers, save files, save editors, cheat mods, codes, fixes and unlockers, and filenames cannot separate them because a table and a save editor both ship as `.zip`. That listing is not table-only either. A game with no Cheat Engine table still has its trainers and saves listed there, so each entry is read through the category it declares in its own container; an entry whose category cannot be read stays listed rather than being dropped. A listing that carried entries and no table is an answer, not a failure, and the game is reported as having no Playground tables; only an unreadable listing degrades to the unfiltered ranking. Acquisition reproduces the site's public anonymous client contract exposed by its own shipped JavaScript: the backend submits the selected file/post identity to `api/file.download`, waits the bounded advertised countdown, exchanges the transient lock token once, and streams the returned protocol-relative CDN link through the shared downloader. It does not crawl robots-disallowed pagination, extract browser cookies, supply credentials, or automate private Steam CEF/CDP. Lock tokens and temporary CDN URLs never leave the backend and are not persisted or logged. Catalog cache entries contain display metadata and canonical source pages, never transient download state or password hints. Playground's page-supplied byte count is display metadata because target evidence shows it may drift from a valid artifact by one byte; advertised SHA-256, when present, remains the artifact integrity authority and the downloader/inspection bounds still apply independently. A stale cache result is labeled and cannot silently reconstruct an expired direct route without refetching the item page.

During the countdown the acquisition remains cancellable and exposes only a decreasing `provider_wait_seconds` value to QAM. A provider that serves out its own wait opens one controller-owned acquisition modal above the catalog so the countdown, transfer, Cancel action, and any archive member/password choice cannot be stranded below a long result list. Playground and VGTimes are those providers, and each is declared as one in the provider registry rather than recognised by name at the screen: both make a guest sit through a countdown their own client contract states, and VGTimes serves a guest one download at a time, so its second acquisition waits for the first as well. A single unencrypted `.CT` imports automatically; a single encrypted member stays in that modal for password input. Import and detached-modal cleanup are serialized so late unmount cancellation cannot remove staging beneath a blocking import, and the acquisition modal closes before Search performs the serial exact-SHA Review handoff. Execution still waits for Review. HTTP 429 preserves bounded `Retry-After` input in provider diagnostics and prevents immediate repeated attempts; the FearLess background index atomically checkpoints its progress, pauses for the same bounded cooldown and resumes the missing listing page instead of spinning or restarting. An acquisition step that answers HTTP 429 is a wait rather than a failure: the acquisition returns to the same cancellable waiting state, shows that the provider is rate limiting rather than preparing anything, and retries a bounded number of times, honouring a bounded `Retry-After` when the provider names one and using a short interactive backoff when it does not. This covers the request that asks a provider for a transient link as well as the artifact transfer itself, because nothing has been spent when that request is refused. The one exception is a limit that lands on Playground's lock exchange, after its one-shot countdown token has been issued and its countdown served: waiting there would replay a handshake the provider has already closed, so that attempt fails with the provider's status. Waiting deliberately does not adopt the background index's own cooldown, whose default minute is longer than the throttle observed on the target, and an attempt fails with the provider's status once the bounded attempts are spent. Nothing else on the download path adopts it either: a table the user has selected is asked for, and a cooldown a failed search recorded never refuses that download before the provider has been given the chance to answer. A wait a provider's own resolver serves out says which kind it is, because a countdown every guest sits through and a provider refusing right now are different things to be told, and a limit a resolver handles inside itself is the only place that refusal is visible. A provider whose own rule is one download at a time keeps its rate limits inside its own resolver, because restarting such a chain would ask for a second handshake rather than repeat a request, and a limit that cannot be waited out there leaves the resolver marked as one the retry layer must not simply run again. A rate limit that was waited out and recovered from is counted in provider diagnostics, with the wait it cost, separately from failed downloads and from the persisted cooldown a terminal 429 sets: a provider that throttles every transfer is otherwise indistinguishable from one that serves files immediately. Every screen that names a provider names the one the artifact is actually coming from.

The frontend selects `provider + artifact_id`; it never supplies a download URL. Direct artifacts pass through the existing archive/table validators and content-addressed store. Table metadata records a bounded, deduplicated origin history per exact SHA. Import remains separate from exact-SHA execution consent.

Provider UI state is bound to exact game identity, including AppID and Steam-vs-shortcut kind. Identity changes invalidate async generations during the committed UI transition, clear old results, and best-effort cancel both already-known and late-returning nonterminal acquisitions before their result can be adopted by the new game context.

## 13. Lifecycle and removal

Frontend routes, subscriptions, patches, listeners, timers, and debounced writes are registered once and removed on dismount. An in-flight read of live cheat state is aborted there too: a refresh walks every actionable record of the table in chunks, which for a large table is over a hundred bridge round-trips, and a dismissed panel must stop that work rather than run it to completion against a component that no longer exists. A mutation the user asked for is not abandoned this way; only reads the panel started for itself. A mutation that outlives its panel therefore completes and reports to a component that is gone, which is an ordinary event rather than an error case: Steam recreates the quick-access browser view while the plugin is working, including when a game returns to the foreground because CE Decky stopped Cheat Engine. Home does not poll its own state, so it re-reads the profile authority and the record of tables that did not work every time the quick-access panel is shown again, and once more as soon as its first status arrives on a panel that was created while the panel was already on screen, which never sees a visibility change at all. That immediate read is issued one round trip after the panel's own first one rather than at a moment related to the write it is racing, so it is followed by a single bounded catch-up read past the far side of the window actually observed on the target. It happens once per panel, behind the first reread that panel performs, and a panel hidden or dismounted before it fires cancels it, because being shown again re-reads anyway. That is what keeps a panel from presenting an execution authorization, a table selection or a mark that was changed while it was being replaced. A loader that cannot report panel visibility loses the re-read, never the panel. Backend cooperative operations are cancelled and awaited on unload. Bounded worker-thread filesystem mutations are drained before unload completes and never promote state after shutdown.

CE Decky can install its own newer release, and does so only on an explicit press. What that press is worth is decided in this order: the newest stable GitHub release is read again at the press rather than taken from the last check, it must be the version the confirmation named, its tag must parse as a version this project publishes and be strictly newer than the running one, the release must carry both its archive and the checksum file published beside it, and the downloaded archive must match the digest that file states. The version is carried from the confirmation into the transaction because the press is consent for a named version: a release published between the screen and the request stops the update and asks again rather than installing something nobody was shown. A prerelease is never offered. Only then is the archive handed to Decky's own loader over its loopback control socket, which is what installs plugins on this device; nothing here writes into the plugin directory, and nothing needs root. Because that install stops and replaces this backend, the process performing it is detached and outlives the plugin, and the record it leaves is read by the backend that loads next: an update that failed keeps the verified archive under the Steam user's home and the panel names that path beside the manual route through Decky's developer mode. What the last update did is said once rather than kept: the next check that answers lets go of an outcome nobody can act on, and the one that stays is the failed install that kept a release, which goes when the file does - installed by hand, deleted, or superseded because this device is already on that version - and a successful update removes that file itself. Installing restarts Steam's interface, which is said before the press, along with the fact that only the download can be stopped. What that window is told afterwards is bounded rather than open-ended: the backend it is asking is the one being replaced, so when it stops answering for longer than a restart takes, the window says the update was handed over and offers a way out, and the outcome is read from the durable record by the panel that comes back. The same is true on the backend's side of that boundary: an installer that exits without reporting settles the operation it was started for, so a device whose install never reached Decky can be told what happened and can try again, rather than holding one update open until something reloads the plugin. Automatic checking is armed by table-search activity and paced, one request at a time, and switching it off stops both the checking and the offer; **Check now** is the press that ignores the arming and joins a check that is already running rather than describing it. What a screen is told leads with the newest thing this device knows: a finding older than a check that failed is named as something found then, the panel withholds its press until a check answers again, and Advanced still carries both the finding and the reason the last attempt did not finish. Reading what a deletion would refuse changes nothing either, which is what the screen saying nothing is deleted by looking means and why the panel reader is allowed to press it: that report asks the updater what is happening and is answered from this process and the durable record, without settling anything. Reading the plugin's status changes nothing about an update: folding in what a detached installer left, writing down when a start time in this clock's future was first seen, and removing a recovery archive this plugin has outgrown all happen where the device is allowed to change - loading, polling an update, starting one, refusing a deletion, and the background tick - because the panel polls that status and so do read-only helpers whose whole value is that looking does not change what they are looking at. An update in flight holds down everything a plugin replacement would interrupt, and it is the panel that adopts it - the window that started it dies with the panel the moment any modal opens, so the press leads back into that window rather than starting a second update.

Decky can invoke uninstall semantics during update and reinstall, so `_uninstall()` preserves settings, profiles, and managed Cheat Engine and table data: it runs on an ordinary plugin update, and deleting the managed root there would destroy the user's own tables, authorizations and downloaded Cheat Engine every time the plugin updates. Removal is an explicit user action instead, and there are two of them. **Manage** removes one exact stored table under the per-table boundary described above. **Advanced → Prepare for removal** handles the fixed bulk scopes and refuses them while anything is still executing out of that tree: a Cheat Engine process CE Decky owns, a managed installation still unpacking into it, or a table download that still owns a staged file. Neither restores Steam state, because CE Decky never writes any: it reads AppDetails, install folders and shortcut storage for identity and owns nothing there to give back.

After bulk deletion, frontend managed authority and in-flight read generations are invalidated immediately. Status and advisory records are reconciled before the workflow settles, including after an uncertain reply; a refresh failure is logged separately and never reverses a committed deletion. A refusal is the case that is not uncertain: the backend checks before it touches anything and says so in the first words of the message, and nothing on the panel's side is reconciled for a deletion that did not happen - which is what kept it from forgetting the game the user had chosen over a Cheat Engine that was still running. The widest scope is a first run on both sides: the panel forgets its own durable choices with the files, and the updater forgets what it was holding in memory because that file could not be written, since storage that will not take writes is exactly why somebody reaches for it.

The bridge automatically attempts to return foreground ownership to the verified game's visible window after attach, dialog suppression and cheat interaction. Attempts are bounded and stop when foreground ownership is already correct. Missing capability, multiple eligible windows and refused activation are diagnostic outcomes. A successful Win32 foreground readback is not a claim that Gamescope controller input recovered; that remains an on-device check.

A new Manage confirmation uses the displayed holder identities after refresh. A newly appeared holder requires another confirmation; games that moved to another table are skipped. Revoke never stops a replacement session. Compatibility survives profile-state repair as history without a current match, and changing target executables requires new evidence even on the same Steam build. Successful autoload startup counts only after the requested leaf activation is observed complete, with no startup failure. Failure history prevents clearing Failed from reviving older success even if the positive record could not be updated.

Foreground recovery is re-armed once startup or rollback finishes, including asynchronous completion after the attach budget expired. An accepted request whose exact handle becomes foreground on a later bounded sweep is counted once as an observed confirmation; that observation still does not prove controller input or causation.

Failed writes and clears are reconciled against the exact current record when the reply is uncertain. Search and Advanced refresh their own detached lists after every clear attempt, including partial clears, without repeating a committed mutation. An unreadable readback is described as an unknown outcome. Invalid failure epochs are visible through the existing repair reason and Clear all rewrites an empty corrupt record too. A stopped selected game still compares its readable Steam build ID; other inactive historical games remain unknown. Device-wide Manage without a selected game shows one neutral historical success per exact table, choosing the newest observation and then the lowest AppID for ties, without claiming a current-build match.

After a confirmed manual activation, Search and Manage receive the new compatibility history even when the separate remembered-cheat or automatic-loading preference write fails. That persistence failure remains visible. Case-only differences in a Windows process basename do not change compatibility identity.
