# Field Notes

What running CE Decky on real SteamOS hardware established, and what is still unverified. Every entry states what was observed, under what identity, by what method, and what would falsify it. Where a number appears, the machine that produced it appears with it.

## 2. Observed behaviour, and what it forced

| Observed | Why the obvious approach does not work |
|---|---|
| Steam and Decky can hold each other in a restart loop that neither one leaves, and only restarting Steam breaks it | Steam Machine, 2026-09-20, after an install whose mandatory webhelper reload reported `timed out` and then fired three minutes later. From `webhelper-linux.txt`, `cef_log.txt` and the system journal: `exec ./steamwebhelper` every 10 to 12 seconds from 18:34:37 to 18:39:02, every one of them under the same `-steampid=1045497`, so Steam itself was healthy and its watchdog was replacing a helper that never finished bringing the UI up; beside it Decky logged `The Tab SharedJSContext socket has been disconnected` then `CEF has disconnected`, exited, and was restarted by its own `Restart=always`, sometimes failing on `OSError: [Errno 98] bind 127.0.0.1:1337 address already in use` because the previous loader had not released the port. Each Decky start re-injects and re-imports every plugin into a UI that has not finished initialising. Neither supervisor backs off, so the loop is stable: it ran for four and a half minutes with nobody touching the device. `pkill -f steamwebhelper` does not break it and takes the client down, because the pattern matches Steam's own processes; the loop ended only when `-steampid` changed, which is Steam being restarted. **What it is not:** the plugin being installed. The same 0.9.29 bundle is what the device settled on, the backend logged `backend.initialize_started` then `backend.initialized` in every cycle, `webhelper_js.txt` holds no error from it, and the panel never mounted at all between 18:24:26 and 18:40:09, so there was nothing of ours running to fail. Every other plugin was stopped and started in the same cycles |
| Decky delivers a plugin method's reply to sockets that did not ask for it, so a fixed request id cannot identify an answer | Steam Machine, 2026-09-19: two identical `target_plugin_rpc.py` calls seconds apart printed one answer twice, while the backend's own journal recorded one call and one operation. Each call opens its own websocket, so a stale reply reaching the second connection is the loader broadcasting it rather than anything the helper kept. The helper drew the same id 91 for every call, which makes a broadcast indistinguishable from this call's answer; an id per call removes the ambiguity, and matching on the route alone would not, because the route is what two identical calls share. What it cost before that: an RPC that never reached the plugin looked like one that had. |
| Steam's own cache names the exact program it starts for an installed game, and the game's folder does not | Steam Machine, 2026-09-14, `~/.steam/steam/appcache/appinfo.vdf`, container `0x07564429`, 345 apps, 2536 keys in its table. For AppID 220 the record holds three Windows launch entries, one per branch, each `hl2.exe` with `workingdir` `bin`, and the public one is spelled `BetaKey` `default` while the game's own `appmanifest` names no branch at all. The same install folder holds 28 Windows executables, 27 of them SDK compilers under `bin/`, which is what a walk of it offers. Counter-Strike 2's record is what forced two of the filters: its workshop tools are a Windows entry conditioned on `ownsdlc` written as a number rather than a string, and its legacy launcher is a second plain entry beside the game. A launch entry's `executable` is install-relative and Windows-spelled, `game\bin\win64\cs2.exe`, so it is resolved component by component against the real directory before it is offered |
| The backend costs nothing measurable while no session is live | Both machines, every unattached window taken on 2026-09-07: the plugin backend does not appear in the CPU groups at all and every counted path reads zero. So a session is the whole of what this plugin costs while a game runs, and the panel's own three-second detector, whose effect depends on plugin status rather than on panel visibility, calls the backend not once while the quick access panel is hidden |
| The bridge heartbeat is not steady-state work | `_await_bridge` returns as soon as the bridge leaves its `starting` phase, so its half-second poll belongs to launch and ends there. It was listed as a live-session cost for a while and was not one, which is why the loops that do run were enumerated from the source rather than from memory |
| A wedged Steam renderer can be read without the debugger, and `ptrace` between unrelated processes is not refused | Steam Machine, 2026-09-13, `kernel.yama.ptrace_scope=1`: `eu-stack -p` walked native frames as user `deck` for all nine `steamwebhelper` processes, the renderer included, returning between 18 and 365 frames each. This was expected to be refused, and the helper was written assuming it would be; the assumption was wrong and is recorded because the next person will make it too. Frames arrive as bare addresses where Steam's binaries carry no symbols, and `eu-stack` prints one walk failure per thread whose unwind information runs out while still returning what it did walk, so success is judged on whether frames came back rather than on whether stderr was empty. The unprivileged `/proc` route needs none of this: per-thread `comm`, `stat`, `wchan` and two processor-time samples separate a spinning thread from a parked one, which is what `target_webhelper_threads.py` reports |
| Chromium renderers under this Steam build report `--type=zygote` for their whole life | Steam Machine, 2026-09-13: a renderer is forked from the zygote and its `argv` is never rewritten, so the command line names the wrong process type and a reader looking for a renderer by name finds none. It is identified by its threads instead, `Compositor` among them. Nothing about this is derivable from the process list alone, which is why the helper reports the declared type and its reading of it separately |
| A block-level repair of a failing scan is provable for some scripts and not for the shape that needs it most | Steam Machine, 2026-09-20, `ct_scan_survey.py --repair` over every scan of 142 corpus tables: 169 of 594 scans in single-scan scripts repair with both proofs passing, 11 of 93 in scripts carrying 2 to 5, and **0 of 96** in scripts carrying 6 or more. The refusals of the last group are one shape: those scripts write every hook's restore in one contiguous `[DISABLE]` block and every hook's labels in one declaration block, so removing one hook's block takes the others with it and the closure proof refuses, correctly. A rule that cut declaration blocks line by line was tried and reverted: it did not repair one more of that group and repaired 61 fewer elsewhere. What the block rule could not reach at all was the `[DISABLE]` run: it declares nothing, so no rule about what a block defines ever sees one, and the line handing a removed hook's symbol back stayed behind naming a symbol that is gone. Taking only a line that is one statement about symbols the repair removed - and nothing carrying a value, an expression or a symbol that survived - raises the corpus to 276 of 783 scans and the tables with at least one repairable scan from 34 of 88 to 56, with 18 fully repairable rather than 4, and leaves the 6-or-more group at 0: what survives there is a scan line in a block held for the scans the table still makes, or an allocation anchored on the hook that went. Two defects were measured out of that number on the way. **125 of the repairs the proofs then accepted removed the script's own `[ENABLE]` or `[DISABLE]` line**, because a script writes a section marker against the block below it with no blank line between them: every symbol still resolved and every record was still the record it was, so nothing refused a table whose cheats could no longer be switched on, or off. And a table's `{ ... }` header, which lists what each hook does symbol by symbol, was read as declarations - handing the removal every symbol it names - while its own blank line ran the comment's tail into the `[ENABLE]` below it. With comments read as comments in both the repair and the proof, and section markers never removed and proven kept, 13 repairs that only passed by reading a header as code now refuse honestly. Of the 276, only **14 leave a script that still scans for something**; 129 leave nothing but the section markers and 133 leave other code. That is the shape of the population rather than a defect: a script carrying one scan is dead when that scan is, which is what the plan says needs no repair at all. It did expose a third: the cost report named only a record reached through an address the removal took, so a repair that emptied a whole script - by far the common outcome - reported **no cheat lost** while the record that was that script became a switch that does nothing. Counting a record whose script the repair emptied takes the table-level repairs that report at least one cheat gone from 101 of 262 to 179, and the ones that empty a script and say nothing was lost to 0. The one 6-or-more script measured outside that corpus repairs exactly - 5 blocks, 34 lines, 963 bytes, no cheat left without an address - because its author wrote one block per hook. The corpus is one provider's, so which shape a user meets is not established |
| Cheat Engine's address list is flat: `AddressList.getCount()` counts every record in the table, nested ones included | Steam Machine, 2026-09-20, `target_ce_launch_probe.py --table` against a real table whose XML holds one top-level `CheatEntry` and 88 nested inside it: the bridge reported `address_list_count=89`. So a walk that reads the list straight through and then follows `Child` on each record visits every nested record twice. The tree is recovered from each record's own `Parent` instead, which the shipped `celua.txt` documents along with `Count`, `Child[]` and `Type` |
| Cheat Engine's public source is older than the shipped 7.7 binary | The project's own issue tracker asks where the 7.7 source is. Source is therefore precedent for API and startup behaviour and never proof of what the exact binary does, so every source-derived assumption that affects the runtime is confirmed against the installed executable instead |
| Cheat Engine's autorun directory cannot be pointed elsewhere | `GetCEdir()` takes it from `application.ExeName`, `InitializeLuaScripts()` reads `<CheatEngineDir>/autorun`, autorun initialisation runs before `HandleParameters()` processes the `.CT` argument, and `NOAUTORUN` only disables extension loading. No command-line contract points autorun at an external directory. A bridge therefore cannot be placed beside a user's own installation while leaving it read-only, which is the whole reason the private runtime copy exists |
| Cheat Engine asks before running a table's own Lua, as a modal form raised from inside `loadTable` | Nothing can answer it. It lands inside the resident bridge's synchronous bootstrap before the bridge has published anything, the window sweep will not close one of Cheat Engine's own forms, and the compositor shows the game rather than Cheat Engine, so the question is never on screen. ## 7. Decisions taken once, and the reason

| Question | Answer |
|---|---|
| Use the native Linux Cheat Engine as the runtime? | No. Upstream itself expects Windows Cheat Engine inside the target Proton environment: its own Linux build's `protonlauncher.lua` copies a Windows installation into `windowsbin` and launches that. Ordinary table compatibility follows the Windows build |
| Use the official Cheat Engine Proton launcher? | Reference only. It corroborates game, compatdata and Proton selection; it is not an architecture dependency |
| Build custom `protonhax` or `wineserver` orchestration? | No. An exact installed Proton tool and an owned process group answer the same need without inventing a launcher |
| Bundle a 7-Zip binary? | No. The host tool is discovered once and used by absolute path, and a device whose build lacks a format's handler drops those rows at search rather than after a download |
| Treat a visible Cheat Engine window as a successful launch? | No. The resident bridge's heartbeat for that exact session is the only success signal; a mapped window is in fact a failure mode, because it takes the game's audio and controller with it |
| Replace a table inside a running Cheat Engine with `loadTable(stream, false, true)`? | No. Public Cheat Engine source maps that third flag to trainer-mode `LoadXML` behaviour: it executes the table's Lua without prompting, which is the exact consent boundary this product exists to hold, and a Lua error there can terminate Cheat Engine. In-process replacement stays post-v1 for its own reasons; this particular shortcut would not be the way to reach it |
| Check the Decky Store's generative-AI attestation to make a submission eligible? | No, and the submission is made without it. The checklist asks the submitter to state that generative AI did not write a majority of the submitted code, and this project cannot state that: `README.md` **Credits** names the models that assisted, and the contract refuses both an inaccurate attestation and scrubbing honest provenance to satisfy a checkbox. The store's own automation does not enforce it, so a submission with the box unchecked is accepted by the description bot and reaches human review; what the one recorded case of a maintainer reaching an unchecked box says is that it is treated as a required item, and that pull request was closed the day the submitter explained why it was unchecked. Read on 2026-09-14 across every open plugin addition and the last hundred closed pull requests of `decky-plugin-database`: no addition created after 2026-04-02 had been merged, the attestation entered the template on 2026-04-10, and additions that died did so from the stale-review automation for want of a third-party tester rather than from the attestation. So the expected outcome of the submission is refusal, the decision is to make it anyway and let the policy be the thing that refuses it, and public GitHub releases are the distribution route that does not depend on it |
| Identify Cheat Engine compatibility by version string? | No. The identity is the exact executable SHA-256, the complete source-tree SHA-256, the bridge SHA-256 and the exact Proton identity |

The pinned tree has no top-level license file; it was used only as API evidence, not as a source-reuse dependency. The API may refuse the request; only readback counts as foreground success.
